# R29 development contract (frozen before relevant source inspection)

Baseline: 9d6841e678ad19a8e961839a2a6f284da3752a66.
Target hypothesis is exposed: a dictionary retained by a keyboard or companion preview may restore pre-clear learned contents after another public instance clears learned words.

1. Explicit Clear Learned Words establishes an empty learned dictionary in the clearing instance and durable storage after a successful save. Every retained writer must respect this reset when next reading/reloading/saving. Contents learned before clear must not reappear merely because a retained writer saves. Already queued pre-clear writes must not undo a completed clear. A later explicit learning action may add the same spelling again.
2. Ordinary saves and reloads preserve valid new local learning and learning saved by other instances. A reset must distinguish pre-reset contents from genuinely new post-reset mutations, including locally unsaved mutations. Explicit forgetting must survive a stale writer's subsequent save; intentional later learning may reintroduce the word. Pin semantics, case normalization and accent distinctions follow the actual public interface once mapped, with no invented capabilities.
3. Tests use sequential deterministic public-instance operations and explicitly ordered interleavings (create/learn/save/clear/reload/forget/pin where available). Distinguish queued writes, own delayed notifications, ordinary external learning, and learning after reset. No timing/sleep oracle. Failed writes must permit a later valid retry without losing unsaved learning.
4. A dictionary with no persistence URL remains in memory, supports its public learning/forget/reset behavior, and creates no persistence files. Storage behavior is language independent unless source demonstrates language-specific semantics; English and Spanish spelling examples do not count as separate language stacks.
5. Clear also clears applicable retained in-memory learned state and tap adaptation if actual app ownership requires it. Source evidence must establish actual creation, retention, notification and save call order before claiming an app bug. No controller change without that evidence.
6. Candidate acceptance requires deterministic baseline counterevidence, an exact executable action/schema/API contract frozen before independent heldout authorship, static heldout validation before sealing, production source freeze and independent review before a single heldout reveal. Preserve all raw outcomes including fail-to-fail and unavailable cases. No post-reveal product tuning.
7. Scope: dictionary persistence/reset and narrowly necessary learning/reset glue only. No KeyboardEngine spacing, emoji search, Settings UI, App/KeyboardPreview.swift or TryItView.swift changes. No per-keystroke blocking I/O, private field/network/auth work, push, merge, deploy, physical devices or parent checkout edits.

This is a development expectation, not an acceptance claim. Actual public API capability map and executable contract will be separately frozen after inspection. Cross-process durability, lock behavior and suspension limits must be reported precisely; a static in-process queue alone is not cross-process proof.
