# Pulpo performance audit — October 16, 2026

This audit follows the web application, shared client preprocessing, iOS/Android
client code, API, Redis replay/routing, and worker context/streaming paths from
baseline `08b2b2328789243f6706452663893f5084e70fa9`. Five independent PRs contain
measured improvements, focused regression coverage, reproducible drivers and
sanitized raw samples. They share the same original base; they are not a stack.
Existing pagination, virtualization and residency work remains in place.

Each PR includes its own report under `docs/performance`, including environment,
raw samples, controls, method limitations and reproduction commands. Shared and
mobile differential checks compare complete outputs with the exact baseline;
regressions use parser/field-access counts instead of machine-dependent timing
thresholds. Reviewers independent of each implementation examined code,
consumers, fixtures, raw medians and claims. Review findings led to additional
socket error containment, effective Redis-configuration guards, source hashes,
benchmark fail-closed checks, and lifecycle regressions.

## Scope and experiment controls

Measurements used an Apple M5 Pro arm64 host with 48 GB RAM, Darwin 27.0.0,
Node 26.12.0 and the repository lockfile. Production-browser fixtures use the
installed Chromium 153.0.8010.12 / Playwright 1.63.0. iOS uses a disposable iPhone
18 Pro simulator on iOS 27.0. Native tests compile actual dependency headers with
Apple Clang 21.0.0. Baseline and changed implementations share dependencies and
fixtures. Warmups, run order and raw sample counts are specified in each report. Web
matrices run baseline then implementation sequentially; other drivers alternate
versions where their reports specify it. Timing runs were separated from builds
and other benchmark runs.

The audit created an isolated PostgreSQL 17 database with vector support and
Redis, on ports 55439 and 56389, seeded only with synthetic chats. The new replay/owner-retention mutation
drivers validate effective Redis configuration, including preview-branch rewrites,
before importing connection code. Existing long-chat drivers retain their
original isolated-database guard; the audit explicitly supplied loopback Redis
and disabled preview rewrites when running them. Neither real accounts nor model-provider calls
were used. Correctness runs made during native builds are explicitly excluded
from performance comparisons. No production capacity, internet latency, provider
token throughput, physical-device FPS, or production Core Web Vitals claim is made.

## Functional and integration validation

The combined changes passed the repository's complete `npm test` command with
`NODE_OPTIONS=--no-experimental-webstorage`, plus repository lint: **4,479 tests
passed** across the default workspace/security/release checks. The runnable
backend suite passed 1,737 tests; 364 environment-gated tests were skipped in
that local default command. CI separately runs database integration tests on
each PR. Shared contracts/client-core, CLI, controller/daemon, web, mobile and
desktop tests also passed. Web/server/desktop/controller/daemon builds and mobile
TypeScript checking passed. Native cache tests passed both normally and with
ThreadSanitizer; explicit Redis benchmark safety tests passed separately from
the workspace test glob.

The production Chromium Markdown matrix retained **54 samples** across three
answer sizes and 20/30/100 Hz cadences, including completion, caret, DOM identity,
draft and focus assertions. Large-account fixtures checked ordering, retained
transcript identity and provisional chats.

A second existing browser harness exercised the real API, PostgreSQL, Redis,
Socket.IO and current virtual transcript on five synthetic cases: 10, 5,000 and
20,000 plain turns, 1,000 rich turns, and 100 oversized turns. All five passed
60-delta stream completeness, concurrent draft value preservation, cached
transcript/draft reload, bottom gap of zero, and reader-anchor movement of zero.
No uncaught page errors or unexpected HTTP error responses were recorded. The
chat-detail endpoint was deliberately blocked during cached reload; this does
not establish whole-application offline startup. These were correctness
runs during native build activity; their timings are not performance evidence.
The driver now enlarges the Resource Timing buffer before bootstrap (otherwise
a full default buffer can omit later history-prefetch entries) and scrolls
with real mouse-wheel intent (programmatic scroll assignment is correctly
classified by the app as a virtualizer correction). App scroll behavior was
unchanged.

Fresh Expo iOS prebuild, CocoaPods installation and a Release simulator build
passed with the actual patched native header. The normal app installed and
launched. A temporary copy of that binary running the existing native UI fixture
passed all three XCTest cases: large Markdown selection, long/cached chat
selection, and gallery navigation from the latest turn. The standalone branch
fixture also checks old/new output equality before timing in Release Hermes;
its retained native samples are documented in #834.

Two pre-existing web test/lifecycle issues surfaced during broad verification.
The dictation test cleared storage before a previous unmount's serialized draft
write completed; its setup now awaits the existing write queue before clearing,
with unchanged assertions and no added sleeps. A CI run passed all test assertions
but failed on a SaveBar timer firing after jsdom teardown. The lifecycle fix
cancels owned timers, ignores save completion after unmount, and prevents an
older confirmation timer from resetting a new save. Focused regressions preserve
the 1,500 ms success confirmation and failure retry behavior.

## Current API pagination scaling control

The existing API driver separately ran on the quiet host against the isolated
seeded database: one discarded warmup, then three retained samples per case,
identity encoding and complete loopback body consumption. These compare current
full-history and current 500-turn-page endpoints, **not old versus new code**.
Database/DTO probes in the raw report are independent calls and must not be
added together to explain the HTTP timings.

| Plain history | Full body / median HTTP | 500-turn page body / median HTTP |
| ---: | ---: | ---: |
| 1,000 turns | 2,201,107 B / 14.8 ms | 1,101,135 B / 11.7 ms |
| 5,000 turns | 11,017,108 B / 67.1 ms | 1,102,634 B / 19.7 ms |
| 20,000 turns | 44,107,112 B / 309.6 ms | 1,104,136 B / 63.1 ms |

The page bounds transferred response bodies for ordinary text, but page latency
still grows with history size: the endpoint fetches path/branch metadata before
selecting bodies. A turn-count limit also does not bound bytes: the 100-turn
oversized-answer fixture still transfers about 30.5 MB even with a 500-turn limit.
Use byte-aware budgets and real account distributions before deriving a network
or memory SLO. These controls support keeping current pagination enabled while
investigating metadata/search/context scaling separately.

The [sanitized validation report](audit-validation-2026-10-16.json) contains all
API warmup/retained samples and browser correctness outcomes, excluding synthetic
session credentials, IDs, raw traces and browser timings collected under builds.
Reproduce with the existing `long-chat-fixtures.ts`, `long-chat-api.ts`, and
`long-chat-browser.ts` workflow documented in `scripts/benchmarks/README.md`;
use an isolated database/Redis and matching loopback ports. The full-stack
correctness selection used `BENCH_VIRTUAL=1 BENCH_REPEATS=1
BENCH_TYPE_DURING_STREAM=1 BENCH_VALIDATE_LAYOUT=1` and
`BENCH_CASES=plain:10,plain:5000,plain:20000,rich:1000,large:100`.

## Remaining work, ordered by evidence and expected impact

1. **Multiple API instances duplicate response broadcasts.** A real two-instance
   Redis/Socket.IO synthetic check measured 50 publications becoming 100 deliveries
   per client and 100 adapter writes. Every process consumes Pub/Sub and broadcasts
   through the cross-process adapter. A `.local` shortcut removes duplication but
   breaks missed-packet connection recovery, so it was rejected. Design single
   fanout ownership while preserving durable recovery and account isolation.
2. **Web live transcript/snapshot retention lacks a complete lifecycle budget.**
   The module-level `accumulatedResponseSnapshots` retains full outputs without a
   deletion/reset path, including across query removal/logout. Seven-day live
   query retention and Zustand loaded bodies are independent of the 25 MiB
   IndexedDB cache budget. This is source-proven reachability, not a measured heap
   growth rate. Define account/query/late-event ownership and prove collection;
   arbitrary eviction can lose stream merge state. Native cache key budgeting
   does not solve this web issue or all native allocations.
3. **Worker context/initial compaction scale poorly on long histories.** Agent
   context reads cumulative snapshots for ancestors while only the latest usable
   context is needed; generation also materializes inactive-branch bodies.
   Initial compaction repeatedly scans remaining history (a 10,000-turn synthetic
   probe took approximately five seconds on this host). Preserve tool protocol,
   compaction, deleted-branch and provider semantics before redesigning these
   paths. See #832's source-level findings and reproducible compaction probe.
4. **Web account list rendering and transfer are still unbounded.** Grouping and
   replacement are faster, but `/api/chats` returns every summary, expanded/root
   sidebar rows are not virtualized, and `chatListRevision` computes an account-wide
   string on store updates even when React avoids a rerender. A dedicated summary
   projection plus a virtual tree needs drag/drop, multiselection, search, menu,
   keyboard and scroll coverage. CPU preparation improvements alone do not bound
   payloads, DOM nodes or per-delta selector allocations.
5. **One huge Markdown answer can still block a frame.** The new web memo skips
   redundant parses but a needed large parse/layout remains synchronous. Shared
   malformed-wrapper regexes can still backtrack. Segmenting/incremental parsing
   requires tables, math, fences, selection and node-identity tests. The iOS cache
   budget trades historical size-cache hits for bounded retained key text; it
   does not bound parser/attributed-string/image/view/transient memory.
6. **Search and snapshot write amplification need workload-specific measurement.**
   Search builds `to_tsvector` from joined serialized response input/output; the
   existing title-only GIN index does not match that expression. Obtain representative
   query plans before changing search. Codex snapshots persist/publish complete output
   every hardcoded 250 ms versus the configurable 1,500 ms default elsewhere.
   Ordinary streaming also awaits Redis operations per event, suggesting RTT
   sensitivity. Measure concurrency, cancellation and reconnect freshness before
   batching or changing persistence cadence.
7. **Mobile collapsed tool output still eagerly serializes payloads.** Large tool
   JSON should be included in future expansion/collapse and scroll fixtures before
   changing serialization ownership. Shared branch metadata now scales well for
   linear chats, but wide distinct-prompt groups inherently emit quadratic total
   control IDs under the existing UI contract.

Existing web pagination/virtualization, per-response persistence, bounded visited
branch windows, bootstrap sharing/reconnect coalescing, and mobile targeted SQLite
reads/residency are useful controls already in the codebase. Earlier audit reports
retain their original hardware and dates; their numbers are not relabeled as
measurements from this audit. A fresh login observation fetched 66 JavaScript
resources totaling 1,037,607 decoded bytes before authentication; no Markdown
chunk was loaded. This is a single current-build observation, not a startup
before/after result or an agreed size budget.

## Platform boundaries

Android source changes share the mobile differential tests and TypeScript checks.
A fresh Android prebuild passed. The configured SDK 37 build encountered an
installed SDK `android-37.0` versus dependency `android-37` naming mismatch. A
local API 36/JDK 21 compatibility build encountered an AAPT2 PNG crunch timeout.
Repeating with PNG crunching disabled produced a Release arm64 APK successfully
(719 Gradle tasks, including native compilation). These were command-line-only
compatibility overrides: compile/target SDK 36, build tools 36.0.0, JDK 21,
`android.enablePngCrunchInReleaseBuilds=false`. The configured SDK 37 release
remains unvalidated; no SDK or PNG setting is changed by these PRs.
Disposable Android emulators failed to boot on this host, so Android Release
Hermes timings and UI/FPS remain unverified. Existing user devices were left alone.

Physical iOS/Android devices, Safari/Firefox, network shaping, production-scale
multi-tenant workloads, model-provider latency, signed app distribution and
production deployment remain outside the evidence collected here. The committed
benchmarks make those follow-ups easier without weakening existing semantics.
