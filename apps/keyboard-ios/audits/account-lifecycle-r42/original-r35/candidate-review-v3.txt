RESIDUAL EVIDENCE FINDINGS

R1. validate.py does not fully validate inputs that the runner silently coerces/defaults.

Evidence: audits/account-lifecycle-r35/validate.py:13-43 checks required keys, basic case/step IDs, host suffix/ownership, response status and checkpoint expected fields. It does not validate optional email/password/code types, signOut.remote type, awaitRequest.path type, or uniqueness of task labels within a case. The runner at AppTests/AccountLifecycleR35BenchmarkTests.swift:94-96 silently substitutes default email/password or omits code when these have the wrong type; line 169 silently treats a wrongly typed remote flag as false.

For example, a signOut step with remote:"true" passes this validator but executes local-only sign-out. A numeric code passes preflight but is omitted from the actual login submission. These are source-derived examples, not inspected fixtures. Duplicate startLogin/startRefresh IDs are retained runtime failures, but can still receive schema:"pass" beforehand. Missing/wrong path types become retained runtime failures rather than preflight rejection.

Consequence: a preflight success is a partial structural check, not a complete public-schema certificate. In the optional-field examples, an input's meaning is changed without a runner failure. Before using schema:"pass" as the validity prerequisite, reject wrong types for all defined fields and duplicate task IDs. This can be addressed entirely in validation, without altering production behavior or using heldout outcomes. No claim is made that the actual sealed fixtures contain these mistakes; they were not opened.

R2. compare.py retains outcomes but does not provide the protocol's separate common-operations comparison.

Evidence: audits/account-lifecycle-r35/compare.py:37-47 requires identical report ID/order, purpose, and recorded input steps, and creates one pair for every supplied record. Every pair retains both failure arrays and both unavailable arrays. summarize at 15-27 aggregates all cases; there is no separate common-operation cohort. A case containing baseline-unavailable revokeLogin contributes baseline and candidate primitive/latency totals to the same overall summaries as common operations.

Consequence: the resulting all-case totals must not be presented as the requested common-operations comparison. Add a separate explicitly defined cohort for schedules using operations supported by both implementations, while retaining all original pairs and all unavailable/failing cases. An unavailable classification takes precedence over fail at 9-12, but failures are still retained in pair fields and runnerFailures; statusCounts alone must therefore not be read as the count of all cases with failures.

Completeness limit: the comparer checks the two supplied arrays against each other, not against an independently sealed fixture ID/count/hash inventory. Two equally incomplete arrays could satisfy pairing checks. The reviewed runner itself iterates every decoded fixture and retains step failures, so no case-dropping path was found in that normal loop. Independent binding to the complete sealed input remains outside the comparison script's guarantee.

CANDIDATE / PUBLIC PROTOCOL ALIGNMENT

1. Pre-cancelled entry is handled before default authorization.
App/AppModel.swift:205-210 checks Task.isCancelled before evaluating attempt ?? beginSignIn(). With no supplied UUID, an unstarted cancelled default call cannot replace newer authority. With an explicit UUID, cancelSignIn only revokes a matching current attempt (199-203); a stale supplied UUID cannot revoke a replacement. The call throws before creating a client or issuing HTTP. No new suspension was added to this entry path.

2. Login authority and actual UI ownership agree.
AppModel:192-203 synchronously authorizes/revokes an attempt and invalidates refresh generation. signIn checks cancellation and matching authority before network, between config/login, and before the synchronous save/memory/snapshot commit (212-237). Its defer cannot clear a replacement UUID. Ordinary/2FA failure preserves the previous account. App/SignInAttempt.swift:21-30 authorizes synchronously before creating the owned Task and captures submission values. Cancel/Back revoke only that UUID and cancel that Task (55-67); SignInView connects Back, Cancel and disappearance (39,76-84).

3. Refresh authority follows the permanent pending-login exclusion.
AppModel:242-264 captures beganDuringSignIn once at actual entry. Both successful publication and unauthorized sign-out require !beganDuringSignIn, the current generation/latest refresh, no pending login, matching instance/token, and a noncancelled task. Later login failure/cancellation/revocation cannot make that captured refresh eligible. A newer refresh identity is not restored after failure/cancellation. Config and me start concurrently, config is awaited first, and both results commit together. Login start/success and sign-out invalidate earlier account authority.

4. Explicit sign-out clears synchronously; remote completion has no later clearing callback.
AppModel:270-286 revokes authority before clear/memory reset/snapshot publication. Remote logout captures the old client/bearer, emits logoutStarted before Task scheduling and logoutFinished in defer after the awaited call. Late remote completion cannot clear a replacement through this closure. The observation establishes call completion, not successful server invalidation.

5. Endpoint/storage/snapshot source agrees within declared scope.
PulpoClient config/login/me/logout endpoints, request body/bearer and nonempty two-factor handling match the protocol. The only candidate/baseline PulpoClient difference is the public PulpoError initializer. Candidate SessionStore uses update then add-if-not-found, checks save success before publication, and does not delete the previous item before an attempted update. AccountSnapshot contains only the four declared fields. Runner checks actual raw snapshot data and rejects extra keys (BenchmarkTests:69-85); reload checks existing memory/store/raw snapshot before constructing another model (171-177). This proves source intent for same-process reconstruction, not process restart, disk flush or crash consistency.

SEAL AND OTHER LIMITS

seal.py hashes the listed account/model/test/project files plus candidate protocol/runner-support scripts and SignInAttempt. Verify compares those selected file hashes. It does not hash the entire dependency closure (for example AccountSnapshot/caller source), assert cross-checkout runner equality, establish built-binary identity, or revalidate actual blind fixture bytes against the stored blindCases metadata. Those guarantees require separate handling; no seal was created or verified here. The hardcoded blindCases metadata was encountered only in the explicitly authorized seal.py source; no heldout path or content was opened.

startRefresh captures state when its Task actually enters the model, not synchronously at the JSON step; schedules needing a particular account/pending-login state must use an issued-request barrier before changing that state. respond is not a task completion barrier. Refresh reports finished because the model consumes errors. Transport-discard sampling can race stopLoading. Teardown timeouts are retained failures but do not guarantee quiescence for subsequent cases sharing the static gate. These limits do not create an identified clean-pass publication defect in the reviewed settled paths.
