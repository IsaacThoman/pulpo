# Files

The Files tab is an account-owned tree of folders, uploaded files, and collaborative documents (`file_nodes`). Chat folders are Files folders too: the sidebar lists the built-in Sidebar folder (`systemRole: 'chats'`), whose chats, folders, files, and shortcuts share one manual order (`GET /api/sidebar`, `GET /api/sidebar/folders/:id/items`, and the other `/api/sidebar` routes, which work with Files turned off; `/api/folders` remains as a flat list for older clients). Chat attachments are separate. Admins can hide it with **Enable Files** in general settings; stored files are kept.

## Tree

Names are unique among live siblings, case-insensitively. Creating or renaming into a taken name fails; uploads, new documents, and restores pick the next free `Name (2)` instead. Folders nest at most 32 levels, and a folder cannot move into its own subtree. Tree mutations take a per-account advisory lock, bump the account revision, and publish the `files` invalidation scope so other sessions refetch.

Trashing marks the whole subtree with the trashed node as its `trash_root_id`; restore returns that batch. An item whose original folder is still trashed returns to the top level. Trashed items are purged under the account's trash retention setting (the same one chats use, default 30 days), but never sooner than 24 hours, so **No retention** only applies to chats. Items trashed before chats and Files shared this setting (the application setting `unifiedTrashSince`, written by migration 0102 or, if it is missing, by the first cleanup to run; admins cannot change it) keep at least the 30 days Files gave them then. Cleanup checks each item again under the account's tree lock, so one restored meanwhile stays. Uploads never confirmed are purged after 24 hours.

The account has one trash for chats and Files items. `GET /api/trash` lists both, newest first, with each item's `purgeAt` (chats as `kind: 'chat'` items); `POST /api/trash/restore`, `POST /api/trash/delete`, and `DELETE /api/trash` act on mixed selections. Chats and Files items keep their own storage and purge paths: trashed chats live in `chats.deleted_at` and are purged by the maintenance worker, while Files items are deleted in the request. With Files turned off by the administrator, the trash covers chats and what the sidebar still shows (folders, and shortcuts to folders and chats). `GET /api/trash/folders/:id` lists a trashed folder's contents (what was trashed with it), so trashed folders can be opened. Restore accepts items inside trashed folders too, which then leave the trash on their own, and an optional `parentId` (null is the top of My files) that puts everything there instead of back where it was, chats included.

On the web the trash is a built-in **Trash** folder at the top of My files (`/files/trash`, and `/files/trash/f/:id` inside a trashed folder), shown by the same browser as any folder: list and grid views, selection, keyboard, and the side panel. It is not stored in Files; views address it with the references in `features/trash/folder.ts`. Dragging items out of it, onto a folder, a breadcrumb, another view, or the sidebar, restores them there; dragging items onto it, or into a view showing it, trashes them. Cut in the trash and paste in a folder restores there as well. Like Sidebar and Archive it can be given a color but not an icon; its color is the account setting `trashColor`, red until changed (null leaves it uncolored). Mobile lists trashed chats from its offline chat store and Files items from `/api/trash`.

Selections act through `POST /api/files/batch/{move,copy,trash,restore,delete}`. Each batch runs in one transaction, so every item changes or none does. A folder listed together with its own contents is treated as the folder alone. Batch moves keep both items on a name clash and return the final names, which lets clients undo a move by moving each item back to its original folder and name.

Copying writes folders and documents in the same transaction that reserves storage for the whole selection. Uploaded files are inserted as pending, duplicated inside the object store (`BlobStore.copy`), then marked ready; a failed object copy removes its placeholder instead of leaving a visible file without bytes.

Document state growth is charged to storage when edits are accepted, before compaction runs. Shrinking a document releases space after compaction discards its earlier snapshot. Asset uploads receive a delayed collection pass after their grace period, even when the document stays idle.

## Side panel

Chats always live in the main view; the side panel holds Files beside them: a folder or a file. The Files browser looks and works the same on the page and in the panel (one header with the path, folder name, and the same icon controls); only the window controls differ: **Split view** on the page, and open in new tab, open in main view, and close in the panel. Folders and files opened in the panel stay there, and the path above a panel file walks back up its folders. Files items move between the two views the same way everywhere: on the page, **Open to the side** (right-click an item, or empty space for the folder being viewed) or Alt/Option-click on an item or path sends it to the panel; in the panel, **Open in main view** or Alt/Option-click makes it the main view and closes the panel. The panel is window state mirrored into `?side=file:<id>` or `?side=folder:<id>` (`folder:root` for My files), so reloads and shared links reopen it and navigation carries it along. The panel is always docked beside the main view, never laid over it. Its width (drag the edge to resize) is clamped to the room beside the sidebar so the main view keeps at least 360px and the panel 320px. When they fit only without the chat sidebar, the sidebar folds away first (the user's own collapse setting is untouched) and returns once there is room or the panel closes; reopening it by hand keeps it open and hides the panel instead. Where two views can never fit (phones), an open panel becomes the only view instead, in place of the main view (which stays mounted and returns when the panel closes), with its usual header controls. If the user keeps the sidebar open when the panel would fit only without it, the panel is hidden but its `side` parameter is kept, so it returns when there is room; meanwhile **Split view** and **Open to the side** are not offered, and Alt/Option-click, file chips, and agent actions open things in the main view instead.

The header's **Open in main view** button (maximize icon, Cmd/Ctrl+Shift+Enter) makes the panel's folder or file the main view: the panel closes and the main view navigates to it, replacing the chat (browser back returns to it). On the web, **Open in new tab** opens the item in its own tab. Cmd/Ctrl+\ hides or reopens the panel. Keys go to the Files view last clicked; before any click only the page listens.

## Grid view

Grid view is a canvas: items can be dragged anywhere, and the view scrolls both ways to reach them. Each folder's arrangement (`file_folder_layouts`: item positions and **Snap to grid**, toggled from the background right-click menu) is stored on the server (`GET`/`PATCH /api/files/layout`), so it follows the user across devices and between the page and the panel. With snapping on, items land in the free cell nearest where they are dropped; turning it on snaps everything. Items without a saved place fill the first free cells row by row; the first rearrangement saves every current place so nothing shifts later. Positions of items that leave a folder are dropped on its next save. The Trash's place at the top of My files is kept under the key `trash`. List view keeps sorting by column.

## Agent files

A chat can be scoped to Files items (`chats.file_scope_ids`): file or folder ids, or `root` for the whole tree. A folder includes every subfolder, and items inside an attached folder (or with the whole tree attached) can be attached as well: they tell the agent what the user pointed out. Each entry has an access mode (`chats.file_scope_access`, keyed like the ids): `read`, `suggest` (the default), or `write`. The composer shows the scope as removable chips (clicking one shows it in the panel), and **Add from Files…** in its **+** menu picks files and folders. Adding items turns on agent mode, because the agent reaches Files only from its workspace. Scopes are validated when set (live items the user owns, at most twenty); an item trashed later stays listed but stops resolving.

Files views offer their items to the chat in the main view, which `ChatPage` publishes as the chat target (the unsent new chat, a saved chat, or none for temporary chats and other pages):

- On the Files page or a file page, **Split view** moves that view into the panel and opens the new-chat page. Cmd/Ctrl+J does the same with the item attached to a new chat (from the panel, it adds the item to the chat on the left).
- Right-click menus offer the agent: **Open in new chat** when no chat is open, **Add to chat** beside the new-chat page, and **Add to current chat** or **Open in new chat** beside a saved chat. On empty space they act on the folder being viewed, or My files.

### The `pulpo files` command

The agent has no Files tools of its own. In its workspace it runs `pulpo files ls|tree|cat|grep|pull|status|push|mkdir|mv|rm|convert` in bash; the CLI (`packages/workspace-daemon`) hands each command to the workspace daemon, which holds it until the server, already polling the running bash operation, answers (see `infra/workspace-image/README.md`). No Pulpo credential enters the sandbox, and the sandbox is the agent's to control, so the server (`apps/server/src/files/agent/relay.ts`) is the only trust boundary:

- Every command's arguments are validated with zod. Paths are walked one child at a time from the chat's scope, re-read for every command, so nothing outside it can be named; `.` and `..` segments are refused and shortcuts are invisible. The only id the sandbox sends is a push's `base.nodeId`, which must match the item its path resolves to. Local paths must be normalized absolute paths under `/workspace/`.
- Paths start with an attached item's name (made unique as `Name (2)`), or at the top of My files for a `root` scope. New items must go inside an attached folder. The system prompt (`files/agent/prompt.ts`) lists every attached item with its access and explains the command.
- The agent sees Markdown documents as Markdown with every pending suggestion accepted (the proposed view), other [live documents](./live-formats.md) as the file their codec exports, and uploaded files as their bytes. In Suggest mode it sees this chat's pending proposal of new content instead, if there is one. `pull` writes them into the workspace (at most 1,000 files or 500 MB per call) with a version for each: the SHA-256 of the proposed Markdown, or the checksum of the bytes. `push` (at most 200 files and 500 MB per call) refuses a file whose version changed since it was pulled, or that already exists when nothing was pulled, unless forced, and reports each file as created, updated, suggested, unchanged, conflict, denied, or error. New names of a live format (`.md`, `.py`, `.txt`, …) become documents of that format; other names become uploaded files, quota-checked, under the per-file cap.
- `cat` and `grep` read documents (their plain text: Markdown, or a text file's content) and text files up to 2 MB. What counts as text comes from the shared file-type table (code, Markdown, CSV, HTML, SVG, notebooks, and `text/*`; never zipped Office files, whose MIME types merely contain `xml`). `grep` takes a JavaScript regular expression (or literal text with `-F`), searches at most 2,000 files and 20 MB, stops after 200 matches, and runs patterns in a separate V8 context with a time budget so one cannot stall the worker. Output is cut to the agent's tool output limit.
- Temporary chats, chats while Files is off, and turns sent through admin chat access get no Files.

### Access modes

What the agent may do with an item follows the nearest attached entry at or above it (`root` covers the rest), so attaching `Projects/` as `read` and `Projects/Plan.md` as `write` makes only the plan writable. A move needs both places to allow changes and uses the more restrictive mode; moving or deleting a folder also takes the modes of attached items inside it, and is refused when one of them is read only. Each change re-checks the mode in its transaction, with the chat row share-locked, so a scope change made meanwhile is never ignored. Built-in folders cannot be moved, renamed, or trashed, and documents keep a name of their format.

- `read`: nothing changes; the agent is told to ask the user.
- `suggest`: every change waits for the owner. Markdown edits become inline suggestions (`mergeMarkdown` in `@pulpo/client-core/doc-schema`) tagged with the reply's change row id, reviewed in the editor. New versions of other live documents are whole-file proposals, reviewed with a diff; accepting one merges it with what users wrote since. New items are created with `file_nodes.suggestion_change_id` set (the agent's later edits to them, and anything it adds inside them, join that suggestion directly); new content for an uploaded file is stored as a kept version; moves and deletions are recorded but not applied. A newer proposal of content for the same file from the same chat supersedes the older one.
- `write`: changes apply at once. Document edits are merged as a minimal Yjs diff (origin `agent`; other live formats through `codec.applyFile`) and broadcast to open editors after commit; uploaded files get their new content under a new object key, and the earlier content is kept as a version.

### Change log, undo, and review

`file_changes` has one row per reply, item, and kind of change (`create`, `update`, `move`, `trash`); a repeated change in the same reply keeps the row's `before` and updates its `after`. Write rows snapshot Markdown documents as ProseMirror JSON read back from the Y document, other live documents as their exported files (kept versions, like uploaded files'), uploaded files as `{ objectKey, sizeBytes, checksum, mimeType }`, and moves as `{ parentId, name }`. `file_versions` holds every stored content of an uploaded file that is not its current one; versions count toward storage and are deleted with their files and accounts. The reply's output carries a `pulpo_file_changes` item (`pulpo.agent.files.changed`) with the number of changed items; the details come from the API:

- `GET /api/responses/:id/file-changes` lists the changes (`FileChangesResponse`). New versions of live documents other than Markdown set `contentDiff` while both versions are kept; `GET /api/file-changes/:id/content/before|after` returns them, and `GET /api/file-changes/:id/text` both as plain text. The web's change list opens them in the format's diff (a line diff for text), and mobile shows the text diff. Document suggestions count their unresolved hunks; once the owner resolved them all in the editor, the row reads as rejected if the document reads as it did before the suggestion (the row keeps that Markdown), and as accepted otherwise.
- `POST /api/responses/:id/file-changes/undo` and `/redo` replay every Write row of a finished reply in one transaction, newest first for undo, each step checked against what the earlier steps left. If any item changed since (a document no longer equals the snapshot, another content replaced a file, an item moved, was trashed, or was restored, or an item the reply created now holds someone else's files, chats, or edits), nothing changes and the answer is 409 `FileChangeConflictBody`, with each conflict and, for documents, the expected and current Markdown.
- Live-file undo and redo use the `restore` codec origin to recover the saved snapshot, including spreadsheet calculation clocks and cached formula results. Restore replaces the saved stylesheet and style indexes, file metadata, collection XML, and package parts (including orphan parts); it does not union them with the version being undone or start a new calculation clock. DOCX restores regenerated source parts even when the modeled content is unchanged. Presentations discard parts absent from the snapshot. Notebook metadata, cells, outputs, attachments, and original JSON layout follow the saved file. Exports must match the saved bytes so the next undo or redo can recognize them.
- `POST /api/responses/:id/file-changes/accept` and `/reject` review every pending suggestion of a reply; `POST /api/file-changes/:changeId/accept` and `/reject` review one. Accepting applies moves and deletions, swaps in proposed content (the replaced content is deleted), resolves a document's hunks, and turns suggested items into ordinary ones; rejecting drops proposals and permanently deletes suggested items, moving any of the owner's own items inside them (live, uploading, or trashed, which stay in the trash) up to where the suggestion was. A suggestion the owner reviewed while the reply was still running starts over if the agent changes the item again. The agent's `rm` withdraws its own chat's suggested items and trashes other chats' like any item.
- `POST /api/files/:id/suggestion/accept` and `/reject` review the suggestion an item belongs to without needing its change row, since backups keep suggested items and inline suggestions but not change history.
- Maintenance forgets a reply's undo history and reviewed suggestions after 30 days (pending suggestions wait), then deletes versions no remaining row needs, object first.

## Uploads

Uploads use the attachment flow (reserve, PUT, confirm) with `users/<id>/files/<node>` object keys and the same per-file cap. Content written later (agent changes, documents turned back into files) gets a fresh `users/<id>/files/<id>` key, so a kept version is never overwritten. Files blobs, including trashed ones, kept versions, and document state count toward the account storage allowance together with chat attachments. They do not reuse the `attachments` table, because chat purges delete attachments claimed by a chat.

## Markdown, text, and other live files

A file's name decides what it is: names of a [live format](./live-formats.md) (`.md` and `.markdown` for Markdown; `.txt`, `.py`, `.json`, `.html`, and most other text and code names for text) are files that can be edited collaboratively, and everything else is an ordinary file. **New file** starts an empty Markdown document, and **New text file** (with any other registered format) one of its own. An uploaded file keeps its original bytes until someone chooses **Edit**. Text and code files then convert at once, because the text format writes them back byte for byte (encoding, byte order mark, line breaks, and trailing newline). Uploaded Markdown opens read-only until then. `GET /api/files/:id/conversion` then does a dry run: it converts the text and reports whether anything would change beyond line endings and trailing whitespace, so the client can show a line diff before `POST /api/files/:id/convert` makes the document. The uploaded object is deleted only after the document commits.

Renaming a document within its format keeps it (`app.js` → `app.ts`). Renaming it to a name of another format, or of none, turns it back into an ordinary file holding its exported bytes (a Markdown document's Markdown), and open editors receive `doc.closed` with reason `converted`. Renaming a file never converts it to a document; that waits for **Edit**. Downloading a document gives its real file (`GET /api/files/:id/export`, or the open editor's own export).

Jupyter notebooks (`.ipynb`) open in a notebook editor once someone picks **Edit**, or at once when created with **New notebook**. It works like Jupyter: command and edit modes with Jupyter's keys, Markdown cells rendered until edited, outputs as the viewer shows them, cut, copy, paste, move, split, merge, and clear or hide outputs. Collaborators' cursors and cells show. Undo covers this session's own edits. Cells don't run in Pulpo; **Run with agent** asks an agent to run the notebook in its sandbox and save the outputs. An unedited notebook downloads byte for byte. See [The notebook format](./live-formats.md#the-notebook-format).

Spreadsheets (`.xlsx`, `.xlsm`, `.xltx`, `.xltm`, `.csv`, `.tsv`) open in the spreadsheet editor, and **New spreadsheet** starts an empty workbook. They convert on **Edit** at once too: workbooks keep every part the editor doesn't change, macros included (never run), and CSV and TSV files keep their delimiter, quoting, encoding, and line breaks. Formulas are calculated in the editor, in downloads, and in what agents pull. Whole-row and whole-column formula ranges retain their logical dimensions across sheets with different used extents; blank tails stay compact during calculation. Structural spreadsheet edits preserve table-column identities and update modeled and preserved references; cut/paste relocates dependent references and attached metadata. Copies capture source positions, formulas, evaluated values, formats and rules before any paste writes, including for filtered rows and overlapping paste-values. Monthly and yearly autofill clamp short months while retaining the original day and time for later steps, including leap years. Large spill copies and metadata lookups use indexed membership. Paste and fill are single undo operations; a cut whose source changed remotely becomes a snapshot copy so it cannot erase that edit. Formula calculations share a work budget, including numeric solvers, value-driven loops, record/criteria products, lookup scans, sorting comparisons and array broadcasting; business-day functions use whole-week arithmetic and indexed holidays. Financial formulas cover coupon schedules, odd-period bonds, duration, accrual intervals, depreciation, annuities and cash flows; their generated oracle grid records documented Excel exceptions to LibreOffice. See [Spreadsheets](./sheets.md).

Text and code files open in CodeMirror (`@pulpo/client-core/office/text/view`). It has syntax highlighting by extension, other sessions' labeled cursors, line numbers, find and replace, line wrapping, and indentation settings. Undo and redo cover the session's own edits. It is read-only for viewers, and colors follow the app's theme. HTML files have a live preview in the opaque-origin sandbox. Mobile runs the same editor in its web view host.

Office engines share the OOXML package reader and writer described in [Live formats](./live-formats.md). ZIP timestamps are fixed so exporting unchanged content keeps the same checksum for agent versions; classic ZIP and ZIP64 entries are checked for consistent headers, actual expanded size, and CRC-32. Ambiguous names, encrypted entries, and malformed packages are refused. Exports write exact sizes and checksums into their ZIP headers with one-shot compression, avoiding streaming-compressor corruption and preserving opaque Office parts such as printer settings.

## Editor chrome

Every live editor on the web (Word, spreadsheets, presentations, notebooks, text) shares the chrome in `apps/web/src/features/files/live/chrome`, so the suite feels like Docs and Office:

- **Menu bar** (`EditorMenuBar`): text menus above the toolbar (File, Edit, View, Help to start). One is open at a time; pointing at another while one is open switches to it, and ArrowLeft/ArrowRight move between them. Closing a menu without a command that moved focus (Escape, a command run) returns focus to the document. Menus are data (`MenuDefinition`, `MenuEntry`: items with platform shortcut hints, checkbox and radio items, submenus, labels, destructive items, and custom content), built when each menu opens, so labels and checked states are current.
- **File menu**: `composeFileMenu(host, parts)` joins what Files offers (`LiveEditorProps.fileMenu`: New ▸ Word document, Spreadsheet, Presentation, or Notebook in the same folder; Make a copy; Download ▸ the native format, the converter's PDF or "print, then save as PDF"; Copy link; Rename; Move to…; Pin to sidebar; Show in folder; Move to trash with an undo toast; Details) with the editor's own (extra downloads such as the current sheet as CSV or TSV, Page setup, Print). Test harnesses pass no host and get the editor's part only. New documents and copies open where this one is shown; trashing leaves for the folder, or closes the side panel.
- **Shared keys** (`useEditorShortcuts`): Cmd/Ctrl+P prints the document (never the app page), Cmd/Ctrl+S confirms the autosave ("All changes saved") instead of the browser's Save Page dialog, and Cmd/Ctrl+/ opens the keyboard shortcuts. They work with focus in the editor; print and save also with focus on the page itself when one editor is in the main view. Keys the editor's own keymap handled are left alone, so Cmd/Ctrl+/ comments lines out in code, as in VS Code.
- **Keyboard shortcuts dialog** (`ShortcutsDialog`): each editor's keys, grouped, in the platform's style, with a search box. Lists come from the engines' keymaps (`docx-shortcuts.ts` is checked against the Word keymap by a test) plus menu items' shortcuts.
- **Controls for toolbars**: `LinkDialog` (Text to display and Link; "example.com" becomes https://example.com, only http(s), mailto:, and tel: links pass, and editors can accept their own targets such as `Sheet1!A1`), `FontSizeInput` (type any size from 1 to 400, a preset list, and −/+), and `ZoomControl` (−, presets with Fit, +; a compact variant for status bars; its buttons keep the names Zoom out, Zoom, and Zoom in, with the zoom as their description, and − and + announce the new zoom).
- **App shortcuts**: the app's own keys (Cmd/Ctrl+K search, +B sidebar, +comma settings, +Backslash panel, +J agent, +Shift+Enter panel to main view) skip keys an editor already handled, and Bold, Justify, Subscript, and Clear formatting pressed inside a Word, spreadsheet, or presentation editor (`[data-file-editor]`, `editorOwnsKey`), even read-only. Code and notebook editors bind none of these, so there the keys stay the app's, as in VS Code and JupyterLab. The chat composer keeps them.

Tests: unit tests sit beside the chrome; the Word, spreadsheet, and presentation browser suites run menu commands, and `npm run test:editor-chrome -w @pulpo/web` drives the text and notebook editors in a harness without a server. `FileDocPage.live.test.tsx` covers the File menu Files provides, the title, and the save status.

Around the editor, the file header says Saved, Saving…, or Offline (Saving… only once a save takes half a second, so typing does not flicker it, and never while the document first loads; `data-sync-state` carries the session's state for tests), names the browser tab after the document (without its extension, and only for the main view), and edits the title with the name before the extension selected. A document's title keeps its type: a name without a live format's extension keeps the document's ("Report v1.2" saves as "Report v1.2.docx"), and an extension of another format is refused, since the server would make the document an ordinary file (Files can still change it). Enter returns to the document. New Word, Excel, PowerPoint, and notebook files from the Files page and its sidebar menu open in their editor with the name selected in the title; Markdown and text files are still named in place.

## Viewing files

Uploaded files open in a viewer chosen by their name, then their type (`filePreviewKind` in `@pulpo/client-core/files`). Uploaded Word documents, spreadsheets, presentations, and notebooks offer **Edit** to become collaborative documents. CSV/TSV and notebooks use their viewers until then; chat attachments keep using the read-only viewers. Legacy and OpenDocument formats offer conversion when the server has a converter (see Office files below).

- **CSV and TSV** open as a grid: column letters and the header row stay at the top and row numbers at the left, columns can be resized (double-click a divider to fit), and numbers align right. The file is indexed once and rows are parsed as they scroll into view, and only the columns in view render, so files with hundreds of thousands of rows or hundreds of columns scroll smoothly. Parsing follows RFC 4180 (quoted delimiters, escaped quotes, quoted line breaks, a byte order mark, CRLF or bare CR line ends). A `.csv` that uses semicolons, tabs, or pipes is detected from its first rows. A **Text** toggle shows the file as written; single-column files open as text.
- **Code and text** (every text and code extension in the shared table, plus whole-name files such as `Dockerfile` and `.gitignore`) are highlighted with the chat's GitHub Light and Dark colors, with line numbers, soft wrap (remembered per browser), copy, and find. Lines are virtualized, so multi-megabyte logs open quickly; files over 300,000 characters show without highlighting. JSON is pretty-printed, with the file as written one click away.
- **HTML and SVG** render only in the opaque-origin preview sandbox (`/sandbox.html`, the same one chat code previews use), so a page can run its scripts but never reach Pulpo's cookies, storage, or API. A **Source** toggle shows the highlighted markup.
- **Jupyter notebooks** (`.ipynb`, nbformat 4 and 3) render read-only: Markdown cells with math and embedded attachments, code cells highlighted in the kernel's language with their execution counts, and stream, error (with ANSI colors), image (PNG, JPEG, GIF, WebP, SVG as an image), Markdown, LaTeX, JSON (including arrays and primitive values, with bounded indentation), and plain-text outputs. HTML and JavaScript outputs run only inside the sandbox, one frame per output sized to its content; widgets, which need a running kernel, are named instead. A notebook that cannot be read says why and shows its text.
- In find (Cmd/Ctrl+F while the viewer has focus), Enter and Shift+Enter step through matches. Grid and code search scroll horizontally as well as vertically to reveal the selected result, including in the native mobile viewers.

Text is decoded with a fallback: a byte order mark (UTF-8 or UTF-16) wins, then strict UTF-8, then Windows-1252, so spreadsheets exported on Windows keep their accents. Size limits: Markdown and quizzes 2 MB, text and code 10 MB, HTML and SVG 10 MB, CSV/TSV and notebooks 25 MB; larger files offer a download. Chat attachments use the same viewers for tables, code, and notebooks.

The pieces live in `@pulpo/client-core` so editors, agents, and mobile reuse them:

- `files` (`file-types.ts`): the one table of extensions, MIME types, and families (text, code, Markdown, delimited, HTML, SVG, notebook, document, spreadsheet, presentation, legacy and OpenDocument containers, media, archives) that the server, web, and mobile read. Add formats there.
- `office/delimited`: `indexDelimited` (random access by row, find, column widths), `sniffDelimiter`, `parseDelimitedRow`.
- `office/notebook`: `parseNotebook` normalizes any nbformat into one model; `pickOutputMime`, `parseAnsi`, and `renderNotebookHtml` (a standalone page for sandboxed web views and exports).
- `highlight`: the lowlight highlighter, line splitting that keeps multi-line tokens, find marks, and the token colors.

On iOS and Android, CSV/TSV open in a native grid (Table and Text, find, and tapping a cell shows and copies its full value), and code and text in a native viewer with line numbers, wrap, find, and copy; JSON is pretty-printed. Tabs display at four-column stops in the native text viewer, while copying keeps the original tabs. Notebooks render to one page (`renderNotebookHtml`, math as MathML) shown in the sandboxed web preview, as are HTML files: on iOS the existing `WKWebView` preview, and on Android a new one (`PulpoWebPreviewActivity`) that serves the page from an address only it answers, with the sandbox Content-Security-Policy as a response header, so the page has an opaque origin, no JavaScript bridge, no file access, and no storage, and links open in the browser. Chat attachments of these types open in the same viewers. Files over 25 MB open in the system viewer.

## Office files

With the office converter configured (`OFFICE_CONVERTER_URL`; see `infra/office-converter/README.md`), Files converts legacy, OpenDocument, and iWork office files into the Office Open XML formats Pulpo's editors work with (docx, xlsx, pptx), and exports any office file as PDF. `/api/auth/settings` reports `officeConversionEnabled` and `/api/mobile/config` reports `capabilities.files.officeConversion`; without the converter, clients hide all of it.

| From | Converts to |
| --- | --- |
| `.doc`, `.rtf`, `.odt`, `.ott`, `.wpd`, `.pages`, `.dotx` | `.docx` |
| `.xls`, `.ods`, `.ots`, `.numbers`, `.xltx` | `.xlsx` |
| `.ppt`, `.pps`, `.odp`, `.otp`, `.key`, `.potx` | `.pptx` |

These, and `.docx`, `.xlsx`, and `.pptx`, export as PDF. The table lives in `@pulpo/contracts` (`officeConversionTarget`, `canExportOfficePdf`) and must match the converter's (`packages/office-converter/src/formats.ts`; a test checks).

- `POST /api/files/:id/conversions` with `{ to }` adds the converted file beside the original, which is kept, under the next free name (`Report.docx`, else `Report (2).docx`). Generated names are truncated by Unicode code points to fit the 255-character name limit, keeping the target extension. It lands where the original is when the conversion finishes, and nothing is created if the original was trashed meanwhile. The bytes are stored first and deleted again unless the new file commits; the file counts toward storage and must fit the per-file cap.
- `GET /api/files/:id/pdf` (`?inline=1` for previews) returns the file as PDF; nothing is stored.

Both run while the client waits rather than as a queued job: conversions take a few seconds, the person is waiting for the result, and the converter service already limits and queues work for the whole instance (answering busy when full). Each account may run two conversions at a time (previews, exports, and its agents' conversions included) per server process, fewer than the converter runs at once, both routes are rate limited (20 a minute), and a client that disconnects cancels its conversion. Failures have their own codes: `office_file_encrypted` (password-protected), `office_conversion_failed` (damaged), `office_file_unreadable` (the content is not what the extension says), `office_file_too_large`, `office_conversion_timeout`, `office_converter_busy`, `office_converter_unavailable`, `office_conversion_unsupported`, and `office_conversion_rate_limited`.

On the web, an office file the browser cannot show opens read only with a PDF preview rendered by the server (files over 50 MB skip it), a note that converting makes a copy, **Convert to .docx** (or .xlsx, .pptx) and **Download as PDF** in its header; the Files menu offers both too. The button shows progress, and the result's toast opens the copy. On mobile, office files already open in Quick Look (or the Android viewer); their item menus add **Export as PDF…** (the share sheet) and **Convert to .docx**, with progress on the row.

Agents run `pulpo files convert <path> --to docx|xlsx|pptx|pdf [--output <path>]`. The copy is created like a pushed file, in the mode its folder allows (so in Suggest mode it waits for the user), recorded for undo and review, from the content the agent sees (its chat's pending proposal, if any). Without `--output` it goes beside the original under a free name, which must be inside an attached folder. Without the converter the command says so and suggests converting in the workspace, whose image has LibreOffice (and Jupyter for notebooks); the system prompt tells the agent to render documents and slides to PDF and PNG there to check how they look.

## Documents

Markdown documents are edited as rich text (TipTap/ProseMirror) and stored as Yjs state; other live formats keep their own Y.Doc layout (see [Live formats](./live-formats.md)). The editor schema lives in `@pulpo/client-core/doc-schema` so web, server, and future clients agree on it; changing its nodes or marks requires bumping `DOC_SCHEMA_VERSION`. Each live format has its own schema version: joins announce the versions the client edits (`schemaVersions`, or only `schemaVersion` from older clients, which then edit Markdown alone), and the server rejects a join whose version for the document's format differs.

Clients sync over the account Socket.IO connection in `doc:<id>` rooms:

- `doc.join` sends the client's state vector. The server joins the room, then answers with the update the client lacks and the server's state vector. The client pushes whatever the server lacks. This handshake runs on every connect, so it also uploads edits made offline and updates whose acknowledgement was lost.
- `doc.update` is appended to `file_doc_updates` before it is broadcast to the room. Clients coalesce keystrokes for 50 ms and keep one update in flight.
- `doc.awareness` relays cursors and selections without persisting them. A join asks peers to resend their state, and leaving or disconnecting removes the session's cursor.
- Trashing or deleting a document sends `doc.closed`, and the editor becomes read-only.

API instances hold no documents in memory. Loading merges `file_docs.state` with every remaining log row in one repeatable-read transaction. The worker's `file-docs` queue compacts the log: it locks the document row, folds the rows it read into a garbage-collected snapshot, deletes exactly those rows, and refreshes the derived `markdown` column (the document's plain text, `codec.toText`). A sequence watermark is not used because identity values can commit out of order. Maintenance reschedules compaction for any document left with pending updates.

Markdown is derived, not authoritative. Export and previews use it; imports and future server-side edits convert Markdown to the schema and apply it with a minimal `updateYFragment` diff, never by replacing state, because other replicas would merge old content back.

Web keeps each opened document in IndexedDB (`pulpo-doc:<account>:<doc>`) for instant loads and offline editing; these databases are removed on sign-out.

## Presentations

PowerPoint decks (`.pptx`, `.potx`, `.ppsx`, `.pptm`, and their macro-enabled siblings) are a live format. **New → New presentation** makes one, and uploaded decks become editable with **Edit**. People co-edit and present them on web, desktop, and mobile. Agents pull, push, and suggest real `.pptx` files. The engine in `@pulpo/client-core/office/presentation` provides a lossless codec, a Yjs layout built for co-editing, a renderer, an editor view core, and review diffs. See [Presentations](./presentations.md).

## Word documents

Word files (`.docx`, `.dotx`, `.docm`, `.dotm`) are live documents of the `document` format; the engine (codec, collaborative model, paginated editor, review diff) is described in [Word documents](office-documents.md). **New → New Word document** creates one from a blank template, uploaded Word files offer **Edit**, and downloads and agent pulls export the current state as a `.docx` (unchanged parts byte for byte, macros dropped from `.docm`). Pictures and copied XML dependencies (including chart and embedded-object parts) are stored as document assets by SHA-256 and served from `/api/files/:id/assets/:hash`. Copies between Word documents or stories transfer their relationship graphs before insertion and remap every reference on export; external links are preserved without being fetched. Custom-marked and automatically numbered notes share the same accepted inventory for agent reads, screen/print rendering, and pagination; custom marks do not advance automatic numbering. Agents read text from the same semantic accept-all resolver used by the editor, including paragraph joins and table revisions, in both current and proposed versions (`pulpo files cat` and `grep` use the codec's `toText`: `#` headings, list labels, `|` table rows, notes, and comments) and push `.docx` files edited with any tool (python-docx, docx4j, LibreOffice); a push is merged into the live document as a minimal diff, so concurrent edits survive, and in Suggest mode it becomes a change the owner reviews in the format's redline (web) or as a text diff (mobile).

In the Word editor, inserted tables start typing in their first cell, pasted tables leave typing after the table, and new footnotes/endnotes open their note editor for typing. Other insert commands keep the caret after the inserted content. Printed body blocks and stories use each section’s text width for wrapping and pagination, and note references and note bodies share their configured numbering format, starting value, and restart policy.

Concurrent splits of the same Word paragraph can duplicate text when the replicas sync, including edits made offline. See the [reproduction, root cause, and migration scope](office-documents.md#concurrent-paragraph-split-limitation).

## Mobile

The iOS and Android app (`apps/mobile/src/features/files`) browses and edits Files natively. It shares the logic the web uses through `@pulpo/client-core`: `doc-sync` (the provider and session controller), `doc-editor` (the TipTap extensions, formatting commands, and suggestion review), and `files` (scopes, sorting, change labels, and Markdown diffs). `GET /api/mobile/config` reports `capabilities.files` (`enabled` and the server's `docSchemaVersion`). With Files off, the drawer hides its Files row and lists only folders and shortcuts to folders or chats, and Files screens say so. An app built for another schema version opens documents read-only and asks for an update.

- **The drawer is the web sidebar.** Below Pinned (pinned chats and Files items in one order), it lists the Sidebar folder's chats, folders, documents, files, and shortcuts in their shared manual order, or the top level by last activity in recent order. Folders (and shortcuts to folders) open in place with their contents, which load once opened; which ones are open is kept per account on the device. There is no separate Folders list. Folder and item menus follow the web's: New Folder Inside, Open in Files, Pin, Rename, Move to Folder (the Sidebar folder's tree, the Archive, or any folder in Files), Move to Archive, and Move to Trash with undo; chats gain Move to Archive. The heading above the chats has New Folder and a menu with New Document, Upload, Sort By, and Open in Files. The sidebar's state and opened folders are kept on the device, so they show at launch and offline, and a folder created offline is sent once the connection returns; other changes to Files items need a connection. Chats filed at the top of My files, or in folders the sidebar does not show, appear in search but not in the drawer, as on the web. Servers without `/api/sidebar` (before 0.156) get their chat folders from `/api/folders`, shown the same way but holding only chats.
- **Browsing** uses native lists, menus, and sheets: Files in the drawer, the built-in Trash at the top of My files, sort and search, selection, move, duplicate, rename, pin, trash with undo, the app's viewers for CSV/TSV, code, text, and notebooks (see Viewing files), Quick Look (or the system viewer) for other uploaded files, and **Edit** for uploaded Markdown. `pulpo://files[/f/<id>|/d/<id>|/trash]` links open these screens (as on the web, `/d/` is any file: a document opens in the editor and an upload in its viewer), and so do links to the instance's own Files pages tapped in replies or documents (full URLs or `/files/…` paths, as agents write them). Pinned folders, files, and shortcuts share the drawer's Pinned list with pinned chats, in the web's order. Listings are cached, so folders seen before still open offline, and the instance's configuration is remembered, so Files is there after starting offline too. A link to an item not seen on the device says it can't open while offline. Tree changes need a connection.
- **Uploads** (photos, the camera, and the document picker) are copied into the app's Documents folder and queued per account in the local store. The queue survives restarts and waits for a connection, and while an administrator has Files turned off (a failed system transfer is tried again after 30 seconds, and reported after three failures); it uploads only while its account is signed in, and before trying again it checks what became of the last attempt's placeholder: one the server confirmed after all finishes the upload, and one still waiting for its bytes is released. Uploaded and downloaded bytes stay in the cache folder, within the download limit chat attachments use, and are fetched again once the item changes.
- **Editors** share a locked-down web view host: on iOS a `WKWebView` served from `pulpo-editor://`, and on Android a `WebView` at `https://pulpo-editor.local` with a `WebViewCompat` message listener. Both use a non-persistent store, a CSP with no network access, no navigation, and recovery after a web-content crash. Markdown uses TipTap, text/code uses CodeMirror, Word uses its pageless view core, spreadsheets use their grid, presentations use their slide editor and presenter, and notebooks use phone-sized cell cards. Each format has its own toolbar and generated page, built with `npm run build:editor`; freshness tests check every page. The app fetches images and preserved parts by hash over the bridge. **Add** offers every format supported by both the app and server; uploaded live files offer **Edit**. Native formatting controls include Word comments and Suggesting, spreadsheet format/row/column menus, slide presentation controls, and notebook cell/output commands. Editor codecs and DOM dependencies stay out of the app's Hermes bundle.
- **The app owns each document.** One `DocSessionController` per open document holds the Y.Doc, joins its room over the account socket, and stores it in SQLite as a snapshot plus an update log. Edits made on the device are flagged until the server acknowledges them. The web view holds a disposable copy that a state-vector handshake keeps in step, so a crashed or reloaded page loses nothing; its final state is merged back as it closes. Closed documents stay connected for up to 30 seconds to finish uploading, and leaving the app writes what open documents have pending at once. On every reconnect, copies with unsynced edits are opened in the background just long enough to upload them; one that closed before its edits were uploaded (a save failed) is tried again while connected, less often each time. Compaction merges what is stored instead of replacing it. Copies with unsynced edits are never evicted (the 60 most recently opened clean copies are kept), and a document trashed elsewhere keeps its unsynced copy until it is restored. A document that becomes an ordinary file (renamed away from Markdown) has its copy removed, so one made from the file later starts afresh rather than receiving the old content. A copy with unsynced edits that a newer version of the app stored is left as it is until that version is back (older editors might drop what they can't show). **Restore** and **Retry** start a new session for the document; anything still typed in the old one is merged into it. Signing out removes the account's copies, cached bytes, and queued uploads; its confirmations (including signing this device out from Devices, and changing servers, which signs out every account) say when documents have edits that haven't been uploaded yet.
- **Chats** show their Files scope as chips above the composer, with **Add from Files** and the access mode for each item. A reply that changed Files shows its changes with undo, redo, and suggestion review, including the conflict details when undo is refused. Tool activity names the `pulpo files` command the agent ran.

CSV/TSV exports validate preserved fields against the output delimiter and quote character (with doubled quotes as escapes), and reuse them only while they still describe the current value. Invalid or stale preserved text is encoded from the cell value; preserved row endings accept only CR, LF, or CRLF. Typed numeric text with surrounding whitespace or line breaks stays text, while exact numeric spellings such as `007` retain their original spelling. Valid untouched imports keep their original bytes, including ragged rows, quoting, line endings, encoding, and BOM.

Spreadsheet sort/filter behavior is documented in [Spreadsheets](sheets.md). Shared sorts move complete row identities so concurrent edits follow their records; partial-width sorts use bulk paste semantics. Filters are recalculated after sorting and the operation undoes in one step.

## Large collections in Files and Office code

File contents and formula ranges can contain more entries than JavaScript accepts as call arguments. Use the shared `@pulpo/client-core/collections` helpers (`maxOf`, `minOf`, `pushAll`, `insertAll`) or a loop for input-sized collections. DOM child lists use `replaceChildrenWith`, which builds a fragment first. The extrema helpers keep `Math.max`/`Math.min` semantics, including empty iterables, NaN and signed zero; callers retain any format-specific empty-range defaults.

Oxlint's local `pulpo/no-input-sized-arguments` rule rejects non-literal argument spreads into `Math.max`, `Math.min`, and `.push` in client-core Office/Files, server Files, and web Files/viewers. It permits fixed array literals without inner spreads. Tests with bounded fixtures are excluded. Run `node --test scripts/lint/no-input-sized-arguments.test.mjs` to check the rule itself.

When reviewing other calls, also check `apply`, `splice`, `unshift`, DOM methods, and byte-to-string conversions. Array/object spreads and `new Set(iterable)` do not expand call arguments and can stay. Remaining production argument spreads were checked: text decoding uses chunks of 8,192 or 32,768 code units; document/presentation base64 encoders use 32,768 bytes; statistical pair helpers return exactly two arrays; clipboard forwarding takes the three arguments of `DOMSerializer.serializeFragment`; the presentation notes pane adds at most one node; asset GC adds at most one predicate; and the live-format query uses the six entries of `LIVE_FORMATS`. Keep these bounds explicit when changing those paths. Large-array tests cover the helpers, changed formula functions, and chunked text decoding. Mobile bundle input hashes include the collection helpers.

Document socket lifecycle tests derive each live format's supported version from its exported schema constant and check that the preceding version is rejected. Spreadsheet version bumps therefore exercise the current handshake without requiring test literals to be updated.
