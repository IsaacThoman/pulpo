## Findings and reachable order

1. **High — a product-generated queued extension save can undo a completed reset.** `UI/PulpoKeyboardViewController.swift:120–123` forwards disappearance to `KeyboardController.hostDidDisappear`; that calls `engine.save(inBackground: true)` (`UI/KeyboardController.swift:420–428`). Engine save first accepts pending learning, then saves dictionary and touch state (`Core/Input/KeyboardEngine.swift:1514–1519`). `PersonalDictionary.saveInBackground` captures a full snapshot and queues an unconditional atomic replacement (`Core/Dictionary/PersonalDictionary.swift:341–368`). `App/AppModel.swift:229–234` clears through fresh instances in the app process. Its serial queues cannot drain the extension's separate queues.

   Source-permitted order: extension learns → disappearance enqueues snapshot S → extension write is delayed → app clear successfully writes empty state → extension's queued S replaces it. No simultaneous visible keyboards or arbitrary public method injection is required. An already-running write delayed before replacement has the same problem. This is a feasible scheduling counterexample, not an observed iPhone reproduction or a claim about frequency.

   Appearance does not necessarily repair it: the late write updates that retained instance's file stamp (`PersonalDictionary.swift:368`); `reloadIfChangedOnDisk` waits for its own process queue, compares the now-current stamp, and can return false (`379–390`). It may instead load the already-resurrected file. The passing save-completes → clear → appearance.reload → learn sequence excludes precisely this interleaving.

2. **Medium — public instance operations lose unrelated learning/forget decisions, but their general UI reachability is narrower than their API reachability.** Full saves never reconcile external contents (`333–368`). Reload replaces memory and clears dirty state (`379–390`), including unsaved local learning. Thus the supplied retained-dirty-save, old+new-after-clear, external-save/local-reload, and stale-save-over-forget/learning failures follow directly. A clean retained instance's plain save is a no-op; the dirty/retry or queued-snapshot prerequisite matters.

   Controllers for the same personal URL share one personal dictionary and touch model **within a process** (`UI/KeyboardController.swift:243–264`); language replacement shares those same objects (`Core/Dictionary/LanguageStack.swift:27–39`). They are not independent competing full writers. The app and extension remain independent writers, and delayed ordinary saves can also cross a process handoff. This supports persistence conflict handling, but not an assertion that arbitrary two-instance learn/clear/learn/reload sequences are reproduced by normal UI navigation or that two active typing owners are established by source.

3. **No proven ordinary preview reset ordering defect.** The preview saves on end editing and removal (`App/KeyboardPreview.swift:198–208,227–231`), reloads through `hostWillAppear` on beginning editing/controller attachment (`150,198–201`), and invalidates its host on removal. Try It drops focus on disappearance (`App/TryItView.swift:91`). Settings routing clears the navigation path (`App/PulpoKeyboardApp.swift:199–209`); reset is on the home/settings screen (`134–137,171–177`). The app targets iPhone and disables multiple scenes (`project.yml:13,46–47`; `App/Info.plist:45–49`). In the ordinary route, preview save precedes clear, app-process dictionary initialization drains earlier dictionary writes, and touch reset/save drains earlier touch writes. Reappearance reloads both (`UI/KeyboardController.swift:347–353`).

   The fresh clearing objects do leave retained shared objects unchanged until reconciliation. Source does not prove those hidden objects perform a fresh post-reset save before appearance in the ordinary single-scene route. Do not turn mere retention, UIKit teardown possibilities, or hypothetical repeated callbacks into proof for a new global controller-clearing hook. Single scene also does not order or eliminate the extension process.

## Ownership semantics and the unavoidable ambiguity

A retained W last observed generation G. Compare (A) W.learn(x), external.clear(), W.save() with (B) external.clear(), W.learn(x), W.save(). With no shared observation at learn, W's local mutation record and the empty durable state at save are identical. Replaying x violates reset in A; discarding x loses true new learning in B. A per-instance delta log alone cannot solve this. Existing `lastUsed` timestamps are not a causal protocol; pin/forget also lack equivalent event ordering. The same ambiguity applies to an unobserved forget versus an intentional later relearn. A notification delivered later cannot retrospectively establish the missing order.

The principled feasible contract is **learning belongs to an observed ownership epoch**: reconcile at ownership acquisition before accepting new input; a successful reset revokes older epochs; stale pending writes cannot commit; later learning in a newly observed epoch is preserved, including the same spelling. Ordinary external saves within an epoch must reconcile valid operations rather than invalidate every writer. Describe the deliberate limit: learning after wall-time reset but before observing it cannot be guaranteed to survive. If the frozen contract requires both histories above to be distinguished without another synchronization boundary, reject that requirement/product candidate rather than claim compliance.

For a candidate, keep mutation capture in memory on the typing path; reconcile at appearance/ownership, explicit reload, and commit. Track local learn/count/pair/pin/forget operations against a baseline, not just stale totals. Merge ordinary external changes with those operations; forgetting needs persistent conflict metadata and an explicit observed-relearn/commit-order policy. Preserve exact spelling counts/pins while applying forget/block semantics by `TextNormalizer.key` (case/diacritic/apostrophe folding, `Core/Dictionary/Lexicon.swift:391–417`); lowercase pair histories and transient contact/replacement words have separate existing semantics. Do not infer resets from an empty file or any changed inode. Failed commits must retain retryable operations without duplicate application.

## Cross-process and tap boundaries

A durable reset epoch/revision plus a cooperative cross-process transaction around **read current revision → validate/reconcile → commit** is a defensible direction. Validate when the queued write executes, not only when it is enqueued. Every saving/resetting process must participate. A process-local queue, unconditional atomic rename, or unlocked check-then-write is insufficient. If using POSIX locks with atomic file replacement, use a stable lock object rather than the inode being replaced. A shared database transaction is another possible mechanism; neither is an implemented or validated recommendation here.

Locks order cooperating commits; they do not invalidate retained memory, discover when an unobserved keystroke happened, guarantee successful storage, or guarantee bounded progress. A blocked/suspended holder cannot be assumed to release on demand; platform suspension/termination behavior needs explicit validation and a non-hanging failure/retry policy. Do not break a held lock based on elapsed time. Apple's archived [TN2408](https://developer.apple.com/library/archive/technotes/tn2408/) documents POSIX-lock-related termination behavior and historical coordination/suspension issues; it specifically says the iOS 8.1 coordination issue was fixed in 8.2, so it is not proof of that old deadlock on this iOS 18+ app. Apple's [extension guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html) calls for synchronized shared-container access. These support the need for coordination, not a claim of modern-device liveness certification.

`performExpiringActivity` is best effort: Apple documents assertion denial/expiration and impending suspension ([API documentation](https://developer.apple.com/documentation/foundation/processinfo/performexpiringactivity%28withreason%3Ausing%3A%29)). The dictionary's expired branch does not cancel its queued write (`PersonalDictionary.swift:345–349`); it supplies no reset barrier.

**Touch adaptation is explicitly in reset scope.** The UI promises to forget touch adjustments (`App/PulpoKeyboardApp.swift:177`), and AppModel resets/saves a separate TouchModel. Its background snapshot likewise unconditionally replaces storage, with its own process-local queue/stamp (`Core/Geometry/TouchModel.swift:139–158`), so it has the analogous late resurrection race. Appearance reload alone has the same limitation. A dictionary-only epoch fix cannot claim complete product reset. Define a reset boundary covering both stores, including partial failures; current two writes are not one transaction. Touch learning is nonlinear/clamped and decayed (`110–136`), so do not assume subtracting snapshot totals yields correct replay. Fresh-epoch tap learning must survive while revoked-epoch snapshots must not. Full Access/fallback also bounds scope: app reset uses group URLs or nil; it cannot erase the extension's inaccessible local fallback (`Core/Shared/AppGroup.swift:28–46`). Transient lexicon words are intentionally not persisted and are not cleared by dictionary clear.

**Disposition:** Proceed only with a narrowly specified dictionary/touch persistence protocol and deterministic ordered cross-process verification, after resolving the ownership contract. Reject controller/preview/engine/UI changes on the present lifecycle evidence, and reject any claim that all real-time post-reset public mutations can be preserved without observing the reset. No candidate is accepted by this review.
