Pulpo R53 — independent source / implementation-plan review

Scope and evidence
Reviewed production Swift source only under /tmp/pulpo-r53-ui-preferences. The task identifies baseline 9ff451f4; no diff or historical comparison was read. No audits, reports, tests, test results, builds, device interactions, or timing measurements were consulted or performed. No other workspace was inspected. This report separates confirmed source defects from risks a proposed implementation must close. Runtime behavior and OS sound policy were not independently demonstrated.

Verdict
The intended outcomes are not satisfied by the reviewed source. Three concrete gaps are visible: swipeTrail has no rendering consumer; emoji picker/search click sites bypass sounds; hold/slide cursor entry bypasses cursor permission and can consume the search separator. A controller-only cursor guard or a global sound flag is insufficient. The narrow change should connect rendering preference independently of recognition, route existing click requests through owner-scoped sound policy, and make cursor authorization part of the contact state machine.

Source paths below are relative to apps/keyboard-ios/ unless otherwise stated.

1. HIGH — Show Slide Trail is offered and persisted but does not control the trail.
Evidence: App/PulpoKeyboardApp.swift:97-99 exposes separate swipeTyping and swipeTrail controls. PulpoKeyboardKit/Sources/KeyboardCore/Shared/KeyboardSettings.swift:12-13,35-36 persists both. In production source, swipeTrail has no UI rendering consumer. KeyboardUI/KeysView.swift:455-457,583-591 unconditionally begins/adds the trail after glide recognition. Input/InputTraits.swift:81 correctly bases allowsGlide on swipeTyping, independently of swipeTrail; KeyboardController.swift:1153-1162 delivers the path to insertGlide.
Concrete failure: turn off Show Slide Trail while leaving Slide to Type on, return to the keyboard, glide a word: the drawing is still requested.
Narrow recommendation: expose a drawing-only preference on KeysView, apply it at initialization and settings reload, and gate only trail begin/add/display activity. Preserve Tracking.points/times, glide recognition, delegate delivery, decoding, word insertion, fallback, spacing, and cancellation. Do not put swipeTrail into allowsGlide or return early from the glide gesture path. A hidden line must still insert the decoded word.
Additional lifecycle risk: GlideTrail.finish() fades rather than immediately clears the layer path (KeysView.swift:858-867), while begin() sets opacity back to one. If preference updates can occur while a trail is active or fading, explicitly stop its display link and clear/hide its layer immediately; avoid an old-line flash on reenable. Keep tracking sample indexes coherent when drawing is skipped. This is a prospective implementation edge, not evidence of an existing live preference notification.

2. HIGH — Sound off still makes three unconditional UIDevice click requests.
Evidence: KeyboardUI/EmojiPanelView.swift:298-303 (normal emoji insertion, also reached by physical/accessibility tone choice through chooseTone at 366-369), :429-432 (picker delete), and EmojiSearchBarView.swift:139-142 (search-result insertion) call playInputClick directly. Only KeyboardController.swift:622-625 and :1165-1167 guard with settings.sounds.
Concrete failure: ordinary key clicks stop with Sound off, but picking an emoji, choosing its tone, deleting from the picker, or choosing a search result still issues a click request. OS muting may make a request inaudible, which does not satisfy the explicit zero-request outcome.
Narrow recommendation: make one sound-only helper owned by the controller/its feedback object the sole UIDevice click sink. Route all five existing request sites through it. Ordinary search typing uses searchTouchDown -> feedback and must stay covered; key-grid repeats use keysViewRepeatDelete and must stay covered. Do not merely change enableInputClicksWhenVisible: that can affect audibility without preventing the requests. Review the source inventory of playInputClick after the change to ensure only the guarded sink remains.

3. HIGH — Search-space hold/slide enters trackpad UI and can lose the separator even though the host is guarded.
Evidence: KeyboardController.swift:1237 returns !isSearching for keysViewAllowsCursorMovement, but KeysView.swift:413-416 schedules hold entry unconditionally; :461-464 promotes horizontal slides; common enterCursorMode at :594-601 never checks the permission. It dims all caps and emits emphasis. Cursor movement at :435-441 marks cursorMoved BEFORE invoking the delegate. The controller rejects movement during search at :1179-1183. Cursor release at :524-529 inserts a space only when cursorMoved is false.
Concrete failure A: in a nonempty search query, hold space without moving: labels disappear during the contact even though no cursor exists. Release still appends the ordinary query separator.
Concrete failure B: hold space, then move at least one cursor step: KeysView records movement, controller declines it, release adds no separator. A slide entering cursor mode has the same failure after a subsequent step.
Narrow recommendation: check current permission in the common cursor-entry function before mode, stats, anchor, dimming, timer, or emphasis changes. Both timer and slide promotion must use that function. Denied entry should keep the contact behaving as a space, with no retarget to a letter/control and normal single activation on noncancelled release. Keep the controller guard as defense in depth. Query space normalization intentionally ignores leading/repeated spaces and stops at the maximum length (KeyboardCore/Emoji/EmojiSearch.swift:17-32); preserve that existing separator policy rather than unconditionally appending a literal space.

4. HIGH — An entry-only permission check does not handle revocation after entry.
Evidence: KeysView's .cursor move branch never rechecks permission; its cursorMoved flag is sticky once set, but currently means attempted view movement. Permission is currently !isSearching. Production mode changes call cancelAllTouches (KeyboardController.swift:112-121), so a normal switch into search cancels existing contacts; do not claim this currently bypasses that cancellation. Nevertheless, the requested midcontact revocation contract requires the view to handle a delegate permission change independently of a root-mode switch.
Concrete cases the implementation must distinguish:
(a) enter cursor mode, no accepted host movement, permission turns false: immediately restore labels when revocation is processed; reject all subsequent host steps; a noncancelled lift retains ordinary space behavior.
(b) enter and genuinely move the host, then permission turns false: restore labels and stop further steps, but retain the fact of earlier movement so lift cannot insert an unintended space at the new caret.
(c) revoke, then grant again before the same finger lifts: do not replay displacement accumulated while denied. Prefer latching revocation for that contact until its terminal event; otherwise explicitly reanchor and define reentry behavior.
(d) revoke just before lift with no further move event: terminal handling must reconcile permission too. A move-only check leaves stale dimming/state until release.
Narrow recommendation: keep contact-local movement history separate from current permission/mode and denial/revocation state. Reconcile authorization before entry, before every cursor step, and at terminal handling. A denied step must neither set movement history nor move the anchor as though movement succeeded. Never clear prior accepted movement just to restore labels. Do not solve revocation by calling activate or committing a space immediately; cancellation must still win.
If immediate undimming at the exact policy-change instant is required, event-time checks alone cannot provide that while a finger is stationary. Provide a narrow explicit refresh/invalidation hook when the owner changes policy; otherwise describe the guarantee as reconciliation on the next contact event.

5. MEDIUM — The source cannot currently distinguish host displacement from a dispatched request.
Evidence: KeysViewDelegate.moveCursor returns Void (KeysView.swift:14); KeyboardHost.adjustTextPosition also returns Void (KeyboardHost.swift:15); the controller's host is weak (KeyboardController.swift:174) and is optionally called. PreviewHost.adjustTextPosition may return early or clamp at document boundaries (App/KeyboardPreview.swift:25-43). The extension simply forwards to UITextDocumentProxy (PulpoKeyboardViewController.swift:171-173).
Concrete risk: setting cursorMoved before the callback counts rejected search movement, a missing host, and boundary/no-op requests as genuine movement. Moving it after the callback without any result still cannot distinguish these cases. A Bool that means only "delegate invoked" does not meet a literal "genuine host movement" contract either.
Narrow recommendation: make the movement acceptance boundary explicit. At minimum return whether a live authorized host accepted a nonzero movement request, and record history only for accepted requests; preserve history through later revocation. If literal observed caret displacement is required, provide a meaningful host acknowledgment where possible and state the UITextDocumentProxy limitation: its Void API and asynchronous/possibly unavailable context do not prove movement synchronously. Do not infer rejection solely from an unchanged immediate context snapshot. Resolve this semantic boundary before claiming the stronger outcome.

6. MEDIUM — Weak global current feedback is not reliable ownership for a new sound preference.
Evidence: KeyboardFeedback.current is a static weak pointer (KeyboardHost.swift:106-108), assigned in every controller init (:301) and hostWillAppear (:358), and not cleared on disappearance. UIKit-retained instances are explicitly anticipated in KeyboardController.swift:190-192. Panels use global current for haptics while their editing callbacks remain tied to their own weak delegates/closures.
Concrete risk if sounds is added to current: another controller initializing or appearing can redirect a visible panel's sound policy to the wrong keyboard. Nil current can silence Sound-on requests; a retained hidden owner can supply stale preference. Weakness prevents ownership retention, not cross-instance misrouting. Unconditionally clearing current on disappearance can erase a newer controller's ownership.
Narrow recommendation: route sound requests through the emitting panel/search bar's weak owner callback or explicitly supplied feedback instance whose lifetime/settings belong to that controller. Do not capture the controller strongly in callbacks retained by its root view. If retaining a global design, require owner identity/visibility checks, identity-conditional clearing, and fail-closed behavior when ownership is absent. Refresh sound state on every appearance/reload, including an already existing picker/search view; avoid construction-time snapshots and avoid defaulting to sound-on when feedback is unavailable.

7. MEDIUM — Sound policy must remain independent of haptics, edits, history, and repeat cadence.
Evidence: KeyboardFeedback.enabled gates only haptics at present (KeyboardHost.swift:110-143); controller feedback calls haptics before its sound guard. EmojiPanel.insert does feedback, history.use, and delegate insertion; chooseTone persists preference before calling insert. Search-result insertion records history and edits in KeyboardController.swift:780-783. Picker repeat callbacks (:435-446) currently issue deletion without additional click or haptic requests; the initial picker delete does issue both. Key-grid repeat requests a click but no haptic at :1165-1176.
Concrete risks: wrapping an entire interaction in `guard sounds` disables edits/history; reusing haptic enabled as the click guard makes sounds depend on Full Access or Haptic Feedback; changing key() to always emit sound gives previously haptic-only suggestion/menu/navigation calls new clicks; routing repeats through a combined feedback method adds haptics/clicks absent before.
Narrow recommendation: use a sound-only operation alongside existing haptic operations. Preserve ordinary, alternate, picker, tone, result, delete/undo, and history actions regardless of sound state. Preserve existing repeat feedback cadence and cancellation; the picker repeat currently has no click to suppress. Check all four sound/haptic combinations, with Full Access independently controlling the existing haptic eligibility.

8. MEDIUM — Preference reload and Full Access semantics constrain the public promise.
Evidence: SettingsStore.load returns defaults when storage is absent or the complete object fails decoding; sounds and swipeTrail default true, and missing keys retain defaults (KeyboardSettings.swift:24-43,55-58). Controller loads at init (:274-275) and hostWillAppear (:354-359), selecting App Group for Full Access/in-app and .standard otherwise (:383-386). sync/documentDidChange do not load settings. App/PulpoKeyboardApp.swift:65-70 explicitly says app changes do not reach the installed keyboard without Full Access. AppModel.settings saves to its shared store (:27,40).
Concrete risks: changing app preferences while a keyboard instance remains visible does not refresh its cached settings; new sound/trail UI state updated only at construction remains stale on reuse; after Full Access removal and reappearance the local store can restore true defaults even when the app's shared Sound or Trail is off. Regrant must switch back to the shared store on appearance. App preview always reports Full Access true (KeyboardPreview.swift:20-21), so preview success does not establish limited-access behavior. Malformed settings also restore true defaults; the source does not promise fail-silent storage recovery.
Narrow recommendation: apply drawing and sound state through one owner update path used by both init and hostWillAppear after store selection/load. Preserve established limited-access local preference behavior and existing user explanation. State whether the guarantee is for the currently loaded effective preference after reappearance, or add an explicit live reload mechanism if immediate cross-process updates are required. Do not introduce fresh App Group reads on every key event or use Full Access itself as a sound/trackpad permission. Full Access is unrelated to ordinary cursor capability; haptics retain their separate existing restriction.

9. MEDIUM — Cursor fixes can regress cancellation, release-only gestures, and multi-contact typing.
Evidence: touchesEnded removes a tracking from the dictionary BEFORE calling move on coalesced samples (KeysView.swift:319-337). begin commits earlier tap contacts before a new finger's action (:374-383). enterCursorMode currently checks mode only; timers hold Tracking. end and cancelAllTouches have distinct semantics (:497-565,765-778). A cancelled space is not rescued by the short-character-tap exception because Key.isCharacter excludes space (KeyboardLayout.swift:47-49).
Concrete risks: requiring dictionary membership in the common entry function rejects valid release-only slide recognition because the terminal path already removed the tracking. Demoting an already moved cursor contact to an ordinary uncommitted tap makes a second finger commit an unintended space. Delayed callbacks without active-contact/committed guards can redim after a roll or cancellation. A generic terminal fallback that inserts space on cancellation changes the current cancellation contract.
Narrow recommendation: validate active identity/committed state in scheduled entry callbacks, while deliberately accommodating the terminal path if the common entry function gains liveness checks. Preserve inert committed contacts, invalidate timers on termination, restore labels on all exit paths, and keep cancelled gestures from adding separators. Preserve normal authorized hold/slide, including hold without movement inserting a space and movement suppressing that insertion. Avoid a blanket cancelAllTouches policy for ordinary permission rejection: that loses the desired separator and can disturb other active keys/modifiers.

Review acceptance scenarios (reasoned requirements, not executed tests)
- Loaded Trail off + Slide to Type on: no rendered line; same path/timestamps reach decoder and word/fallback insertion. Trail on restores drawing; Slide to Type off still disables recognition independently.
- Loaded Sound off: zero UIDevice click requests from ordinary keys, query keys, key-grid repeats, picker emoji/tone/delete, and query results. Haptics and all edits/history remain independent. Existing no-click picker repeats remain no-click.
- Sound on: retain UIDevice.playInputClick and both extension/preview UIInputViewAudioFeedback conformances (PulpoKeyboardViewController.swift:4-8; KeyboardPreview.swift:238-240). These are the existing source mechanism intended to respect OS clicks. Source review does not establish audible output under every system/ringer condition; do not bypass OS policy with another audio API.
- Nonempty query space tap, stationary hold, horizontal slide, and release-only coalesced slide: ordinary normalized separator, no cursor-mode labels/emphasis, zero host movement requests. Cancelled variants add no separator. Leading/duplicate/capped query behavior stays unchanged.
- Allowed ordinary trackpad: hold and slide work; no-movement release retains a space; accepted movement prevents a space; cancellation cleans up without insertion.
- Permission false before entry, revoked before first accepted movement, revoked after accepted movement, revoked then restored during the same contact, revoked just before release, and missing owner/host: no unauthorized movement or stale dimming; preserve the distinction between prior movement and no movement.
- Reused controller reloads shared preferences on appearance, uses local/default settings without Full Access, restores shared settings on regrant, and does not borrow another instance's feedback policy.

Unresolved objections before approval
The reviewed source has the confirmed failures in items 1-3. A prospective R53 implementation should answer the contact-state and feedback-ownership risks explicitly. In particular, the meaning of "genuine host movement" versus an authorized proxy request, and the required latency of midcontact revocation while stationary, need precise implementation contracts. No unpublished implementation was read, so this report neither endorses nor alleges defects in such an implementation.
