# R23 UIKit ownership diagnosis — acceptance remains incomplete

Parent independent review supports the narrow runtime diagnosis. **The original R21 standalone acceptance test remains enabled and failing; its document checks after all consumers release remain UNEXECUTED.** The observed UIKit cycle does not justify changing an app strong edge, weakening that test, shipping private UIKit manipulation or declaring full acceptance. This import adds audit artifacts only: no production changes, registered tests, expectation changes or test skips.

R23 observed iOS Simulator 27.0 build `24A434`, arm64, UIKitCore UUID `E9CBEBE9-BFEE-3385-AF52-D32C606E46BE`. It established `UIInputView → _UIInputViewContent → same UIInputView`, with the ordinary app-owned `PreviewInputView → controller → engine` chain retained beneath it. This is evidence about that runtime, not every OS/device, documented intended lifetime or an Apple-confirmed bug. It does not exclude every possible app leak.

## Independent verification

The targeted [candidate pointer transcript](evidence/candidate-pointer-and-content-methods.txt.gz) closes both sides using read-only SBProcess reads in synthetic PID 67042: input `0x116b74000`, left `0x11809c380`, right `0x11809c540`, and both content `_inputView` values equal the input. The separate [probe](evidence/candidate-probe.txt) reports host nil and surviving controller/engine. The transcript includes `_UIInputViewContent` initializer calling `objc_storeStrong` at +128 and destructor clearing the same field. [UIInputView disassembly](evidence/input-initializer-and-destructor.txt.gz) passes itself to the two content initializers, stores their results and adds them as subviews.

Captured [runtime metadata](evidence/strong-layout-and-ivar-offsets.txt) independently marks input offsets 440/448 and content offset 432 strong. For each class, decoding starts at the aligned superclass size 416; each layout byte skips its high-nibble word count, then scans its low-nibble word count. `11 12 b6` includes input offsets 440/448; `21` marks content offset 432. Weak layouts are empty. The metadata output is in the native run log, **not** the corresponding LLDB transcript: that expression's `printf` output went to the test process. The retained excerpt captures the actual output.

The [plain UIKit reference trace](evidence/plain-uikit-strong-incoming-reference.txt) and [plain UIKit pointer description](evidence/plain-uikit-closed-pointer.txt) independently show input `0x10aca8780 → content 0x10ad1e840 → same input`. That control builds only a `UIInputView` plus a plain `UIView` child, with no Pulpo host/controller/engine, feedback, handler or task in its constructed hierarchy. It still runs inside the synthetic app process. The reverse trace's value after the ivar annotation denotes the field location; the actual back-pointer value comes from the separate ivar description. Other stack/raw-layer references are conservative paths and do not independently prove ownership. The [preview reverse-reference excerpt](evidence/preview-strong-incoming-reference.txt) is an earlier, separately addressed capture; its addresses must not be conflated with PID 67042.

Source inspection confirms weak host/handler/queued captures and weak static feedback storage. The controller-without-input and plain UIView controls release; the input controls do not. Together these facts support the measured UIKit cycle and do not prove that it is the only possible retention mechanism.

The separate living-host comparator keeps its host alive for the **entire process** via `comparisonHosts`, so baseline `f17109e7`'s unowned adapter remains valid during asynchronous callbacks. Both [baseline](evidence/baseline-living-host-failures.txt) and [candidate](evidence/candidate-living-host-failures.txt) fail the same input/controller/engine nil assertions. It establishes comparable consumer retention while the host lives; it does not satisfy standalone host-release acceptance or safely validate the original crashing baseline after host release. [Source proof](source-proof.json) anchors both adapter versions to immutable hashes. The run summaries/log excerpts do not themselves attest a build-time source hash for the temporary baseline file swap; the comparator provenance also relies on the original investigator's account. The UIKit-only evidence does not depend on that swap.
