# Independent R45 boundary author package, v1

This is pre-execution authoring material for adversarial validator review. It is not a product run, a successful paired-run claim, or an epoch/race proof. No private numerical offset constants or implementation assumptions are supplied.

## Counts and identity

There are **24 independent top-level boundary families**, **34 mode instances**, and **652 planned checks**. Repeating a family in memory and persistent modes is not another independent family. Seeds, multiple rejected calls, normalization checks, saves, reloads, and individual scalar/array comparisons are checks within the named family. `denominators.json` fixes each instance denominator. `fixtures.json` also fixes the total and per-instance denominators. The runner checks these against its own static plan before execution.

## JSON schema

The root has `schemaVersion: 1`, `authoringPhase`, `publicMapSHA256`, `busyRetryCount: 0`, two fixed numeric tolerances, `uniqueFamilyCount`, `instanceCount`, `plannedCheckCount`, and `families`.

A family contains `id`, `rationale`, and `instances`. An instance has unique `id` equal to `mode` (`memory` or `persistent`), `steps`, `roundTrip`, `nilSave`, and `plannedCheckCount`. IDs are safe lowercase filesystem components and validated before use.

Each step has a fully explicit `payload`, optional fully explicit `control`, `expectedAccepted`, `weightRule`, nullable `statusRule`, `settleAfter`, optional `learning`, and `expectedActualSamples`. Payloads have literal `text`, literal `intended`, a materialized array of optional taps, and optionally literal `normalizedText`. No fixture text, control, target, expected sample count, result, or expectation is generated by the Swift runner. The sample annotation is author-declared metadata, not a count inferred from model behavior. It is retained in results and never used to derive acceptance.

A tap is `null` or `{key, dx, dy}`. `key` is one literal lowercase ASCII key. Coordinates use the public qwerty center of that key plus literal displacements. Each displacement is a finite JSON number or exactly `nan`, `+inf`, or `-inf`. The runner uses an explicit `[KeyPoint?]` array to construct `TypedWord`. Optional-array holes and a shorter-than-text array are distinct intentional fixtures.

## Fixed oracle rules

The primary and control learning flags are explicitly enabled at construction; a learning-off step then explicitly disables the primary. Acceptance is an explicit Boolean per step. Every accepted step independently requires a finite, strictly increased public weight and successful local-control acceptance. Every rejected step independently requires bit-identical weight and every offset component; this is stricter than tolerant equivalence and includes the sign of zero. There is no guessed absolute weight unit or offset constant: the approved public map specifies neither. Thus a positive weight change is the direct accepted-weight oracle, and exact zero delta is the direct rejection-weight oracle.

Every step also compares public weight and all offsets to a separately constructed nil-URL local control. The entire explicit control history is fixed in the JSON. Rejected steps add nothing to that control. Sparse-long controls are ordinary short inputs with the same intended contributing key/sample order and the same per-call grouping. Expansion controls duplicate the explicitly specified source tap. Ignored-tap controls replace ignored positions with nil or omit extra taps. Corrected-spelling controls use the intended aligned spelling. The twelve-call accumulation family preserves all twelve call boundaries. Initial fresh-state equality and subsequent short-control equality do not claim a private zero state or a private formula for offsets.

Control and roundtrip comparisons require finite values and use `abs(a-b) <= 1e-12 + 1e-12*max(abs(a),abs(b))`. Exact no-mutation comparisons do not use this tolerance. All offset entries, array lengths, and both coordinates are compared.

Persistent oversize rejection has fixed `invalid` status. Other status rules are null/capture-only because the map explicitly allows diagnostic changes and does not mandate a particular non-busy status for every other rejection, nil-URL save, or unchanged reload. All operation statuses are retained. Save success is a fixed assertion for persistent seeded settlement and persistence roundtrips. Nil-URL save return and unchanged-disk reload return are captured without inventing unspecified Boolean meanings; their state/file effects are still checked.

## Boundary coverage and limitations

The independent families cover minimum two-byte validity; long dense memory; long sparse local alignment with missing trailing taps; equal-length corrected spelling; expansion duplication; corrected spelling with expansion; ignored extra nonfinite taps; ignored nonletter nonfinite taps; contributing NaN; contributing signed infinity; normalized alignment mismatch; omitted/all-nil samples; empty and underlength targets; learning-off; isolated nil-URL no-files behavior; short sparse persistence; dense forty; long sparse forty; long sparse one; seeded dense forty-one rejection; seeded sparse forty-one rejection; expanded forty; expanded forty-two rejection; and accumulation of more than forty samples across bounded calls. Families containing two related invalid calls remain one family. The largest accepted same-key repetition is well below 300. There is no maximum-weight decay expectation, timing race, old witness reuse, epoch inference, or coordinator-lifetime assertion.

Roundtrips synchronously save, assert save has not changed local state, reopen the public URL, compare reopened state against both the pre-save state and the explicit local control, and invoke public reload without external changes. The first model remains alive; this intentionally tests ordinary save/reopen compatibility and does not assert release of a registry entry.

## Filesystem authority and nil URL

The executable requires a fresh, nonexistent absolute output directory. Each instance receives its own empty directory under `isolated-work/`, with no reused URL. Persistent requested names are exactly `TouchModel.json`. Public `storageURL(for:)` is captured and must remain within that instance's fresh directory, otherwise the instance is an error. Recursive snapshots include the whole instance directory, all entries and the root, not merely one guessed JSON filename. Requested/authority URLs and all file snapshots are retained in output.

Snapshots record membership, file type, inode, device, raw file bytes (base64), and exact `lstat` modification seconds plus nanoseconds; symlink targets are captured without traversal. Directory metadata is included. Atime is intentionally absent. This is a directory-scoped assertion and does not claim to inspect the whole host filesystem.

Persistent constructors may create files before the test baseline. No assertion requires a persistent constructor to leave the directory empty. Each rejection baseline is captured immediately before the learn, after its persistent seed has been synchronously saved. A rejection is compared before any later save that could flush earlier work. All persistent rejection families have such an explicit settled seed. Save/reopen may legitimately modify files and does not retroactively weaken a rejection assertion.

For nil URLs the process actually changes cwd to the fresh instance directory before constructing either model; the original cwd is restored on exit. The directory is empty at the primary nil-URL construction baseline. Construction, learning, and explicit nil-URL save use recursive before/after snapshots. Results and fixture files are outside that cwd, so author/output writes cannot make a no-created-files check vacuous. Every nil-URL control is also checked for filesystem side effects, including when controlling a persistent instance.

## Unavailability, errors, and result preservation

There are no retries: the fixed busy retry count is zero. An explicitly observed raw `busy` raises an unavailable outcome, retains the attempted operation event, and labels every remaining dependent planned check unavailable. It never becomes an expected invalid rejection or a passing check. Already recorded passes and failures remain recorded. Other thrown errors label remaining planned checks error. Independent instances and families continue. A failed assertion does not abort the remaining ordinary checks or hide subsequent families.

Every instance result contains the full planned list and check/pass/fail/unavailable/error counts. Every family has a separate JSON and aggregated counts; `results.json` repeats every family and contains global counts. Check count always includes pass, fail, unavailable, and error. Bookkeeping faults are additional explicit error checks, never discarded. Publication errors are separately retained in the aggregate; any such error prevents a complete pass. Runtime events retain actual returns, statuses, states, and rejection before/after files even when busy prevents evaluation.

Exit 0 requires every check to pass and no publication errors. Exit 1 indicates actual failed checks (possibly also errors/unavailability). Exit 2 indicates unavailable/error/incomplete results or setup/output failure. A validator must inspect counts and full results, not just process success. An interrupted or unlaunchable executable is not a successful family run.

## Build and execution contract

Compile the standalone `runner.swift` against the authorized built public `KeyboardCore` module with Swift 6.2 and Foundation. Supply that module's normal include/link settings externally; the runner does not locate or read product files itself. Invocation is `runner /absolute/fixtures.json /absolute/fresh-output-dir`. No build, module typecheck, link, fake product, or executable run was performed during authoring. Only `swiftc -frontend -parse` and author-side structural checks were used. Parsing establishes syntax only, not API type compatibility or behavioral success.

## Freeze and reveal discipline

Expected input, acceptance, weight relation, status requirements, controls, tolerances, and denominator plan are fixed in these artifacts before any product execution. Independent validator review precedes the requested source/runner/input freeze. No claim is made that the validator has accepted or officially frozen these files. Do not dynamically infer expectations from either product revision, retune after source reveal, drop failures, or regenerate fixtures to fit an observed model. A new domain failure discovered after a paired run rejects that round or requires a separately identified author/validator round; it must not be silently repaired in this payload.
