# Files

The Files tab is an account-owned tree of folders, uploaded files, and collaborative documents (`file_nodes`). Chat folders are Files folders too: the sidebar lists the built-in Sidebar folder (`systemRole: 'chats'`), whose chats, folders, files, and shortcuts share one manual order (`GET /api/sidebar`, `GET /api/sidebar/folders/:id/items`, and the other `/api/sidebar` routes, which work with Files turned off; `/api/folders` remains as a flat list for older clients). Chat attachments are separate. Admins can hide it with **Enable Files** in general settings; stored files are kept.

## Tree

Names are unique among live siblings, case-insensitively. Creating or renaming into a taken name fails; uploads, new documents, and restores pick the next free `Name (2)` instead. Folders nest at most 32 levels, and a folder cannot move into its own subtree. Tree mutations take a per-account advisory lock, bump the account revision, and publish the `files` invalidation scope so other sessions refetch.

Trashing marks the whole subtree with the trashed node as its `trash_root_id`; restore returns that batch. An item whose original folder is still trashed returns to the top level. Trashed items are purged under the account's trash retention setting (the same one chats use, default 30 days), but never sooner than 24 hours, so **No retention** only applies to chats. Items trashed before chats and Files shared this setting (the application setting `unifiedTrashSince`, written by migration 0102 or, if it is missing, by the first cleanup to run; admins cannot change it) keep at least the 30 days Files gave them then. Cleanup checks each item again under the account's tree lock, so one restored meanwhile stays. Uploads never confirmed are purged after 24 hours.

The account has one trash for chats and Files items. `GET /api/trash` lists both, newest first, with each item's `purgeAt` (chats as `kind: 'chat'` items); `POST /api/trash/restore`, `POST /api/trash/delete`, and `DELETE /api/trash` act on mixed selections. Chats and Files items keep their own storage and purge paths: trashed chats live in `chats.deleted_at` and are purged by the maintenance worker, while Files items are deleted in the request. With Files turned off by the administrator, the trash covers chats and what the sidebar still shows (folders, and shortcuts to folders and chats). `GET /api/trash/folders/:id` lists a trashed folder's contents (what was trashed with it), so trashed folders can be opened. Restore accepts items inside trashed folders too, which then leave the trash on their own, and an optional `parentId` (null is the top of My files) that puts everything there instead of back where it was, chats included.

On the web the trash is a built-in **Trash** folder at the top of My files (`/files/trash`, and `/files/trash/f/:id` inside a trashed folder), shown by the same browser as any folder: list and grid views, selection, keyboard, and the side panel. It is not stored in Files; views address it with the references in `features/trash/folder.ts`. Dragging items out of it, onto a folder, a breadcrumb, another view, or the sidebar, restores them there; dragging items onto it, or into a view showing it, trashes them. Cut in the trash and paste in a folder restores there as well. Like Sidebar and Archive it can be given a color but not an icon; its color is the account setting `trashColor`, red until changed (null leaves it uncolored). Mobile lists trashed chats from its offline chat store and Files items from `/api/trash`.

Selections act through `POST /api/files/batch/{move,copy,trash,restore,delete}`. Each batch runs in one transaction, so every item changes or none does. A folder listed together with its own contents is treated as the folder alone. Batch moves keep both items on a name clash and return the final names, which lets clients undo a move by moving each item back to its original folder and name.

Copying writes folders and documents in the same transaction that reserves storage for the whole selection. Uploaded files are inserted as pending, duplicated inside the object store (`BlobStore.copy`), then marked ready; a failed object copy removes its placeholder instead of leaving a visible file without bytes.

## Side panel

Chats always live in the main view; the side panel holds Files beside them: a folder, a file, or a chat attachment, each in a tab of the panel's own (see [Side panel tabs](#side-panel-tabs)). The Files browser looks and works the same on the page and in the panel (one header with the path, folder name, and the same icon controls); only the window controls differ: **Split view** on the page, and, at the end of the panel's tab strip, open in new browser tab, open in main view, and close. Folders and files opened in the panel stay in its tab, and the path above a panel file walks back up its folders. Files items move between the two views the same way everywhere: on the page, **Open to the side** (right-click an item, or empty space for the folder being viewed) or Alt/Option-click on an item or path sends it to the panel, in a panel tab already showing it or a new one after the panel's active tab; in the panel, **Open in main view** or Alt/Option-click on an item opens it in the main view and leaves the panel as it is, while **Open in main view** for the panel's own folder (empty space, or the strip's maximize button) moves its tab there. The panel is window state mirrored into `?side=file:<id>` or `?side=folder:<id>` (`folder:root` for My files): the URL holds the active panel tab, so reloads and shared links reopen it and navigation carries it along, and a link or back/forward arriving with another one shows it in the panel's tabs. The panel is always docked beside the main view, never laid over it. Its width (drag the edge to resize) is clamped to the room beside the sidebar so the main view keeps at least 360px and the panel 320px. When they fit only without the chat sidebar, the sidebar folds away first (the user's own collapse setting is untouched) and returns once there is room or the panel closes; reopening it by hand keeps it open and hides the panel instead. Where two views can never fit (phones), an open panel becomes the only view instead, in place of the main view (which stays mounted and returns when the panel closes), with its usual window controls; opening something in the main view from it hides it (keeping its tabs), so the main view shows. If the user keeps the sidebar open when the panel would fit only without it, the panel is hidden but its `side` parameter is kept, so it returns when there is room; meanwhile **Split view** and **Open to the side** are not offered, and Alt/Option-click, file chips, and agent actions open things in the main view instead.

The strip's **Open in main view** button (maximize icon, Cmd/Ctrl+Shift+Enter) moves the panel's active tab to the main view: the tab closes (the panel hides if it was the last) and the main view navigates to it, replacing the chat (browser back returns to it). On the web, **Open in new browser tab** opens the item in its own browser tab. **Close panel** (×, Cmd/Ctrl+\) hides the panel and keeps its tabs, and Cmd/Ctrl+\ brings it back with them (with no tabs left, it reopens the tabs closed last). Keys go to the Files view last clicked; before any click only the page listens. With Files turned off the panel has no tabs: it shows one thing at a time (what opens replaces it), with the window controls in its header, and opening an item from it in the main view closes the panel.

## Tabs

On the web and in the desktop app, Files views sit under a strip of tabs, as in a browser (`features/files/tabs`, rendered by the `FilesLayout` route around every Files route). Each tab keeps its own place: My files, a folder, the trash or a trashed folder, or a file. The view below shows the active tab's place and follows the URL, so opening a folder, a breadcrumb, a sidebar item, or **Open in main view** happens in the active tab. Switching tabs navigates and marks the history entry with the tab, so browser back and forward return to the tab that was showing; coming back to Files (from a chat, or with back/forward) shows a tab already at that place instead of moving the active one. The sidebar's **Files** button returns to the active tab as it was left, and from inside Files goes to My files.

- **+** (or double-clicking empty strip space on the web) opens My files in a new tab at the end. **Open in new tab** in an item's menu (in Files or the sidebar), or a middle-click on an item in Files, opens a folder or file in a tab behind the current one (tabs opened from one tab line up after it); when the main view is not showing Files, the new tab shows there. On the web, items' **Open in new browser tab** still opens a browser tab.
- Tabs are reordered by dragging (they show on press, as in browsers) or with Alt+Left/Right on a focused tab. Pinned tabs show only their icon and stay first. The tab menu (right-click) offers **New tab to the right**, **Duplicate**, **Pin tab**, **Open to the right**, **Close tab**, **Close other tabs** (pinned tabs stay), **Close tabs to the right**, and **Reopen closed tab**, which reopens the last closed tab, or tabs closed together, where they were. The chevron at the end lists every tab and the recently closed ones.
- Tabs close with their ×, a middle-click, or Delete on a focused tab; closing the active tab shows the one to its right. After closing with the pointer, tabs keep their width until the pointer leaves the strip, so the next × lands under it. Closing the last tab goes back to My files in a new tab (a lone My files tab has no ×), and the closed one can still be reopened.
- Folder tabs (including My files and the trash) take items dragged onto them like folders in the list do: Files items and sidebar items move there (or go to the trash), and files from the computer are uploaded into that folder, which the tab then shows.
- A tab's title and icon come from cached Files data, so a tab in the background follows renames seen in any listing; the last known look is stored with the tab. The page title is the active tab's.
- Tabs belong to the window and the account (`pulpo.files.tabs:<account>`): on the web each browser tab keeps its own through reloads in session storage, and a new browser tab starts with one; the desktop app, which has one window, also keeps them in local storage across launches. Signing out forgets them.
- In the desktop app, while Files tabs show (in the main view or the side panel), the File menu has **New Tab** (Cmd/Ctrl+T), **Reopen Closed Tab** (Cmd/Ctrl+Shift+T), and **Close Tab** (Cmd/Ctrl+W: the main view's last tab goes back to My files, and once only an unpinned My files tab is left there, the side panel's tabs close, then the window; closing the window moves to Cmd/Ctrl+Shift+W), and the page takes Ctrl+Tab and Ctrl+Shift+Tab, Ctrl+PageDown/PageUp, Cmd+Option+Right/Left and Cmd+Shift+]/[ on a Mac, and Cmd/Ctrl+1–8 (9 for the last tab). They act on the tabs of the view in use: the side panel's when focus is in it, or it was clicked last, or the main view is not showing Files; otherwise the main view's. Browsers keep these keys for their own tabs, so on the web tabs are used with the pointer or from the keyboard inside the strip (arrow keys, Enter, Delete, Shift+F10).

### Side panel tabs

With Files on, the side panel has its own strip of tabs at its top (`features/side-panel/PanelTabStrip.tsx`, built on the main view's `features/files/tabs/TabStrip.tsx`), which look and work the same: dragging, pinning, duplicating, closing, reopening, the tab list, and folder tabs that take dropped items and uploads (the panel's own browser uploads them). Its tabs also hold chat attachments, named and drawn from their cached data. The panel shows its active tab, and its window buttons for that tab sit at the end of the strip.

- Opening something in the panel from elsewhere (**Open to the side**, Alt/Option-click, file chips, the changes bar, saved-to-Files **Show**, an attachment, **Split view**, a `?side=` link) shows a panel tab already at that place, or opens one right after the active tab, and shows the panel. Browsing inside the panel (folders, the path, **Show in folder**) stays in its tab, and a middle-click or **Open in new tab** on an item in the panel opens it in a panel tab behind the active one.
- Closing the panel's last tab hides the panel (Cmd/Ctrl+\ brings back the tabs closed last); a view's own **Close** (a file that cannot open, a rejected suggestion) closes its tab.
- One document opens in one view: when the main view opens a file or attachment that panel tabs show, those tabs close (hiding the panel if none are left).
- The tab menu offers **Open in main view** in place of **Open to the right**, moving the tab there.
- The panel's tabs belong to the window and account like the main view's (`pulpo.files.panelTabs:<account>`), independent of them, and are forgotten on sign-out.

## Grid view

Grid view is a canvas: items can be dragged anywhere, and the view scrolls both ways to reach them. Each folder's arrangement (`file_folder_layouts`: item positions and **Snap to grid**, toggled from the background right-click menu) is stored on the server (`GET`/`PATCH /api/files/layout`), so it follows the user across devices and between the page and the panel. With snapping on, items land in the free cell nearest where they are dropped; turning it on snaps everything. Items without a saved place fill the first free cells row by row; the first rearrangement saves every current place so nothing shifts later. Positions of items that leave a folder are dropped on its next save. The Trash's place at the top of My files is kept under the key `trash`. List view keeps sorting by column.

## Agent files

Attachments are unchanged; Files items are **mentioned in messages** instead. The composer keeps a message's references in its draft text as a last paragraph of links (`[Plan.md](/files/d/<id>)` for files and documents, `/files/f/<id>` for folders; helpers in `@pulpo/client-core/files` `references.ts` and `@pulpo/contracts` `files.ts`) and shows that paragraph as chips, so synced, shelved, queued, recovered, and edited drafts carry references with nothing of their own. **Add from Files…** in the composer's **+** menu adds references. So does typing `@` at the start of a word in the message box: it lists up to eight of the user's own files, documents, and folders whose names contain the rest of the word (`GET /api/files/search`, which leaves out shortcuts and trash; a bare `@` lists the most recently changed), leaving out items already mentioned. Up, Down, and Enter or Tab choose one on the web, and Escape closes the list for that word; an `@` inside a word, as in an email address, is just text. Choosing an item replaces the `@` word with the item's name as plain text and adds the item as **Add from Files…** does, so the message is the same as typing the name and picking it: nothing about the mention itself is stored (helpers in `@pulpo/client-core/files` `mentions.ts`). A message that mentions Files items needs Agent mode, as non-image attachments do, because the agent reaches Files only from its workspace: adding one turns Agent mode on, and with it off (or unavailable for the model) the composer says so and does not send. In the composer and in sent messages they show as cards beside the attachments (`FileReferenceCard` on web and mobile), the same shape as an attachment's but marked as Files items: a Files badge on the icon, "In Files · Work" with the item's folder (or "No longer in Files") instead of a size, and opening in Files; a sent message's text omits the paragraph, and links elsewhere in it stay inline. When a new or edited message is sent from the app (not regenerated, not through the API or admin chat access, not in a temporary chat), the server adds the live items the owner owns that it links to (`fileReferenceIds`, at most 50 per message; only Markdown links count, the ones shown as cards or chips, not bare paths or links inside code) to the chat's scope (`chats.file_scope_ids`, `scopeWithMessageReferences` in `chats/file-scope.ts`); past 50 entries the oldest make room. The scope is what the agent may use in the chat: file or folder ids, or `root` (all of My files) for chats from before references. A folder includes every subfolder, and items inside a mentioned folder can be mentioned too: they tell the agent what the user pointed out. The **Files access…** entry in the Pulpo Agent menu lists a saved chat's scope, where items can be removed, and whether the agent may browse (see below), which can be revoked there.

Files views offer their items to the chat in the main view, which `ChatPage` publishes as the chat target (the unsent new chat, a saved chat, or none for temporary chats and other pages):

- On the Files page or a file page, **Split view** moves that view into the panel and opens the new-chat page. Cmd/Ctrl+J does the same with the item attached to a new chat (from the panel, it adds the item to the chat on the left).
- Right-click menus offer the agent: **Open in new chat** when no chat is open, **Add to chat** beside the new-chat page, and **Add to current chat** or **Open in new chat** beside a saved chat. On empty space they act on the folder being viewed, or My files. These add references to the target composer's message (`usePendingReferences` in `features/side-panel/agent.ts`, taken by the composer once it is mounted); all of My files is not an item to mention, so it offers none of them.

### The `pulpo files` command

The agent has no Files tools of its own. In its workspace it runs `pulpo files ls|tree|cat|grep|pull|status|push|mkdir|mv|rm` in bash; the CLI (`packages/workspace-daemon`) hands each command to the workspace daemon, which holds it until the server, already polling the running bash operation, answers (see `infra/workspace-image/README.md`). No Pulpo credential enters the sandbox, and the sandbox is the agent's to control, so the server (`apps/server/src/files/agent/relay.ts`) is the only trust boundary:

- Every command's arguments are validated with zod. Paths are walked one child at a time from the chat's scope, re-read for every command, so nothing outside it can be named; `.` and `..` segments are refused and shortcuts are invisible. The only id the sandbox sends is a push's `base.nodeId`, which must match the item its path resolves to. Local paths must be normalized absolute paths under `/workspace/`.
- Paths always start at the top of My files (`Projects/Plan.md`). The system prompt (`files/agent/prompt.ts`) lists every mentioned item with its path and access and explains the command. Unless the agent may browse, a path can only pass through the folders above mentioned items (`FileScope.passThrough`), and naming anything else, listing or searching one of those folders or the top of My files, or creating an item there raises `FilesPermissionNeeded` before anything is revealed, including whether the name exists.
- The agent sees documents as Markdown with every pending suggestion accepted (the proposed view), and uploaded files with this chat's pending proposal of new content, if any. `pull` writes them into the workspace (at most 1,000 files or 500 MB per call) with a version for each: the SHA-256 of the proposed Markdown, or the content checksum. `push` (at most 200 files and 500 MB per call) refuses a file whose version changed since it was pulled, or that already exists when nothing was pulled, unless forced, and reports each file as created, updated, suggested, unchanged, conflict, denied, or error. New `.md` names become documents; other names become uploaded files, quota-checked, under the per-file cap.
- `cat` and `grep` read documents and text files up to 2 MB. `grep` takes a JavaScript regular expression (or literal text with `-F`), searches at most 2,000 files and 20 MB, stops after 200 matches, and runs patterns in a separate V8 context with a time budget so one cannot stall the worker. Output is cut to the agent's tool output limit.
- Temporary chats, chats while Files is off, and turns sent through admin chat access get no Files.

### Asking before browsing

Before running a command, the relay (`files/agent/relay.ts`) checks every path it names. When one needs permission, it asks through the runner (`agent/runner.ts`, helpers in `files/agent/permission.ts`): the reply publishes a `pulpo_files_permission` output item (`pulpo.agent.files_permission`) with status `awaiting_decision`, shown after the turn whose command asked, and holds the command for up to three minutes (`FILES_PERMISSION_TIMEOUT_MS`). Commands arriving meanwhile wait for the same answer. While it waits, the reply keeps touching the workspace (`keepingLease` in `agent/controller.ts`), so a workspace idle timeout shorter than the wait does not remove it under the held command. A bash command that calls `pulpo files` also runs for at least the wait and 30 seconds more (`bashTimeoutMs` in `agent/tools.ts`, within the instance's command limit), whatever timeout the agent gave it, so the command is still there when the answer or the expiry arrives. The reply shows **Pulpo Agent wants to look through your Files** with **Deny**, **Allow for this chat**, and, in its menu, **Always allow reading Files**; `POST /api/responses/:id/files-permission` (`{ itemId, decision: 'allow_chat' | 'allow_always' | 'deny' }`) saves the grant before the reply hears the answer: `chats.files_browse_allowed`, or the account preference `agentFilesAskBeforeBrowsing: false`. The item becomes `allowed`, `always_allowed`, `denied`, or, without an answer, `expired`, and the agent is told to carry on with what it has; a refusal or expiry stands for the rest of the reply, so it asks once. A run resumed after an interruption marks a request left waiting as expired. **Ask before the agent looks through Files** in the Agent settings is the same preference.

Only an app that can show the request is asked. Clients list what they can do in the `x-pulpo-client-features` header (`CLIENT_FEATURES`, here `files-permission`), and the response keeps what the app that sent its message listed (`responses.client_features`; `queued_messages.client_features` until a queued message is sent). For a message from an app that listed nothing, such as an older build, the agent is told it cannot ask, and a command that needs permission fails at once instead of waiting for an answer nobody can give.

### Access modes

Each chat has one change mode (`chats.file_change_mode`, `read`, `suggest`, or `write`), chosen under **Changes to Files** in the Pulpo Agent menu; new chats take the account preference `agentFileChangeMode` (suggest unless changed; choosing in the new-chat composer changes it, as does **Changes to Files in new chats** in the Agent settings). It applies to the mentioned items; items the agent reaches only by browsing get at most `suggest` (`BROWSED_FILES_MODE_LIMIT`). Older clients set modes per item (`chats.file_scope_access`), which still override the chat's mode for those items until the chat's mode is changed, which clears them. Otherwise what the agent may do with an item follows the nearest mentioned entry at or above it (`root` covers the rest, then browsing), so attaching `Projects/` as `read` and `Projects/Plan.md` as `write` makes only the plan writable. A move needs both places to allow changes and uses the more restrictive mode; moving or deleting a folder also takes the modes of attached items inside it, and is refused when one of them is read only. Each change re-checks the mode in its transaction, with the chat row share-locked, so a scope change made meanwhile is never ignored. Built-in folders cannot be moved, renamed, or trashed, and documents keep a Markdown name.

- `read`: nothing changes; the agent is told to ask the user.
- `suggest`: every change waits for the owner. Document edits become inline suggestions (`mergeMarkdown` in `@pulpo/client-core/doc-schema`) tagged with the reply's change row id, reviewed in the editor. New items are created with `file_nodes.suggestion_change_id` set (the agent's later edits to them, and anything it adds inside them, join that suggestion directly); new content for an uploaded file is stored as a kept version; moves and deletions are recorded but not applied. A newer proposal of content for the same file from the same chat supersedes the older one.
- `write`: changes apply at once. Document edits are merged as a minimal Yjs diff (origin `agent`) and broadcast to open editors after commit; uploaded files get their new content under a new object key, and the earlier content is kept as a version.

### Change log, undo, and review

`file_changes` has one row per reply, item, and kind of change (`create`, `update`, `move`, `trash`); a repeated change in the same reply keeps the row's `before` and updates its `after`. Write rows snapshot documents as ProseMirror JSON read back from the Y document, uploaded files as `{ objectKey, sizeBytes, checksum, mimeType }`, and moves as `{ parentId, name }`. `file_versions` holds every stored content of an uploaded file that is not its current one; versions count toward storage and are deleted with their files and accounts. The reply's output carries a `pulpo_file_changes` item (`pulpo.agent.files.changed`) with the number of changed items; the details come from the API:

- `GET /api/responses/:id/file-changes` lists the changes (`FileChangesResponse`). Document suggestions count their unresolved hunks; once the owner resolved them all in the editor, the row reads as rejected if the document reads as it did before the suggestion (the row keeps that Markdown), and as accepted otherwise.
- `POST /api/responses/:id/file-changes/undo` and `/redo` replay every Write row of a finished reply in one transaction, newest first for undo, each step checked against what the earlier steps left. If any item changed since (a document no longer equals the snapshot, another content replaced a file, an item moved, was trashed, or was restored, or an item the reply created now holds someone else's files, chats, or edits), nothing changes and the answer is 409 `FileChangeConflictBody`, with each conflict and, for documents, the expected and current Markdown.
- `POST /api/responses/:id/file-changes/accept` and `/reject` review every pending suggestion of a reply; `POST /api/file-changes/:changeId/accept` and `/reject` review one. Accepting applies moves and deletions, swaps in proposed content (the replaced content is deleted), resolves a document's hunks, and turns suggested items into ordinary ones; rejecting drops proposals and permanently deletes suggested items, moving any of the owner's own items inside them (live, uploading, or trashed, which stay in the trash) up to where the suggestion was. A suggestion the owner reviewed while the reply was still running starts over if the agent changes the item again. The agent's `rm` withdraws its own chat's suggested items and trashes other chats' like any item.
- `POST /api/files/:id/suggestion/accept` and `/reject` review the suggestion an item belongs to without needing its change row, since backups keep suggested items and inline suggestions but not change history.
- Maintenance forgets a reply's undo history and reviewed suggestions after 30 days (pending suggestions wait), then deletes versions no remaining row needs, object first.

## Uploads

Uploads use the attachment flow (reserve, PUT, confirm) with `users/<id>/files/<node>` object keys and the same per-file cap. Content written later (agent changes, documents turned back into files) gets a fresh `users/<id>/files/<id>` key, so a kept version is never overwritten. Files blobs, including trashed ones, kept versions, and document state count toward the account storage allowance together with chat attachments. They do not reuse the `attachments` table, because chat purges delete attachments claimed by a chat.

## Markdown files

A file's name decides what it is: names ending in `.md` or `.markdown` are Markdown files, and everything else is an ordinary file. New files start as empty editable Markdown documents. Uploaded Markdown keeps its original bytes and opens read-only until someone chooses **Edit**. `GET /api/files/:id/conversion` then does a dry run: it converts the text and reports whether anything would change beyond line endings and trailing whitespace, so the client can show a line diff before `POST /api/files/:id/convert` makes the document. The uploaded object is deleted only after the document commits.

Renaming an editable document to a name without a Markdown extension turns it back into an ordinary file holding its Markdown, and open editors receive `doc.closed` with reason `converted`. Renaming a file to `.md` never converts it; it waits for **Edit**.

## Documents

Documents are edited as rich text (TipTap/ProseMirror) and stored as Yjs state. The editor schema lives in `@pulpo/client-core/doc-schema` so web, server, and future clients agree on it; changing its nodes or marks requires bumping `DOC_SCHEMA_VERSION`, and the server rejects joins from other versions.

Clients sync over the account Socket.IO connection in `doc:<id>` rooms:

- `doc.join` sends the client's state vector. The server joins the room, then answers with the update the client lacks and the server's state vector. The client pushes whatever the server lacks. This handshake runs on every connect, so it also uploads edits made offline and updates whose acknowledgement was lost.
- `doc.update` is appended to `file_doc_updates` before it is broadcast to the room. Clients coalesce keystrokes for 50 ms and keep one update in flight.
- `doc.awareness` relays cursors and selections without persisting them. A join asks peers to resend their state, and leaving or disconnecting removes the session's cursor.
- Trashing or deleting a document sends `doc.closed`, and the editor becomes read-only.

API instances hold no documents in memory. Loading merges `file_docs.state` with every remaining log row in one repeatable-read transaction. The worker's `file-docs` queue compacts the log: it locks the document row, folds the rows it read into a garbage-collected snapshot, deletes exactly those rows, and refreshes the derived `markdown` column. A sequence watermark is not used because identity values can commit out of order. Maintenance reschedules compaction for any document left with pending updates.

Markdown is derived, not authoritative. Export and previews use it; imports and future server-side edits convert Markdown to the schema and apply it with a minimal `updateYFragment` diff, never by replacing state, because other replicas would merge old content back.

Web keeps each opened document in IndexedDB (`pulpo-doc:<account>:<doc>`) for instant loads and offline editing; these databases are removed on sign-out.

## Mobile

The iOS and Android app (`apps/mobile/src/features/files`) browses and edits Files natively. It has no Files tabs: its Files screens are a native navigation stack. It shares the logic the web uses through `@pulpo/client-core`: `doc-sync` (the provider and session controller), `doc-editor` (the TipTap extensions, formatting commands, and suggestion review), and `files` (scopes, sorting, change labels, and Markdown diffs). `GET /api/mobile/config` reports `capabilities.files` (`enabled` and the server's `docSchemaVersion`). With Files off, the drawer hides its Files row and lists only folders and shortcuts to folders or chats, and Files screens say so. An app built for another schema version opens documents read-only and asks for an update.

- **The drawer is the web sidebar.** Below Pinned (pinned chats and Files items in one order), it lists the Sidebar folder's chats, folders, documents, files, and shortcuts in their shared manual order, or the top level by last activity in recent order. Folders (and shortcuts to folders) open in place with their contents, which load once opened; which ones are open is kept per account on the device. There is no separate Folders list. Folder and item menus follow the web's: New Folder Inside, Open in Files, Pin, Rename, Move to Folder (the Sidebar folder's tree, the Archive, or any folder in Files), Move to Archive, and Move to Trash with undo; chats gain Move to Archive. The heading above the chats has New Folder and a menu with New Document, Upload, Sort By, and Open in Files. The sidebar's state and opened folders are kept on the device, so they show at launch and offline, and a folder created offline is sent once the connection returns; other changes to Files items need a connection. Chats filed at the top of My files, or in folders the sidebar does not show, appear in search but not in the drawer, as on the web. Servers without `/api/sidebar` (before 0.156) get their chat folders from `/api/folders`, shown the same way but holding only chats.
- **Browsing** uses native lists, menus, and sheets: Files in the drawer, the built-in Trash at the top of My files, sort and search, selection, move, duplicate, rename, pin, trash with undo, Quick Look (or the system viewer) for uploaded files, and **Edit** for uploaded Markdown. `pulpo://files[/f/<id>|/d/<id>|/trash]` links open these screens (as on the web, `/d/` is any file: a document opens in the editor and an upload in its viewer), and so do links to the instance's own Files pages tapped in replies or documents (full URLs or `/files/…` paths, as agents write them). Pinned folders, files, and shortcuts share the drawer's Pinned list with pinned chats, in the web's order. Listings are cached, so folders seen before still open offline, and the instance's configuration is remembered, so Files is there after starting offline too. A link to an item not seen on the device says it can't open while offline. Tree changes need a connection.
- **Uploads** (photos, the camera, and the document picker) are copied into the app's Documents folder and queued per account in the local store. The queue survives restarts and waits for a connection, and while an administrator has Files turned off (a failed system transfer is tried again after 30 seconds, and reported after three failures); it uploads only while its account is signed in, and before trying again it checks what became of the last attempt's placeholder: one the server confirmed after all finishes the upload, and one still waiting for its bytes is released. Uploaded and downloaded bytes stay in the cache folder, within the download limit chat attachments use, and are fetched again once the item changes.
- **Documents** are edited by the same TipTap editor as the web. It runs in a locked-down web view: on iOS a `WKWebView` served from the `pulpo-editor://` scheme, and on Android a `WebView` at `https://pulpo-editor.local` that cannot read files and talks only through a `WebViewCompat` message listener. Both have a non-persistent store, a CSP that loads nothing from the network, no navigation, and a restart if the web content process dies. The bundle is built by `npm run build:editor` into `editorBundle.generated.ts`. A test fails if it is stale, and another keeps TipTap out of the app's Hermes bundle.
- **The app owns each document.** One `DocSessionController` per open document holds the Y.Doc, joins its room over the account socket, and stores it in SQLite as a snapshot plus an update log. Edits made on the device are flagged until the server acknowledges them. The web view holds a disposable copy that a state-vector handshake keeps in step, so a crashed or reloaded page loses nothing; its final state is merged back as it closes. Closed documents stay connected for up to 30 seconds to finish uploading, and leaving the app writes what open documents have pending at once. On every reconnect, copies with unsynced edits are opened in the background just long enough to upload them; one that closed before its edits were uploaded (a save failed) is tried again while connected, less often each time. Compaction merges what is stored instead of replacing it. Copies with unsynced edits are never evicted (the 60 most recently opened clean copies are kept), and a document trashed elsewhere keeps its unsynced copy until it is restored. A document that becomes an ordinary file (renamed away from Markdown) has its copy removed, so one made from the file later starts afresh rather than receiving the old content. A copy with unsynced edits that a newer version of the app stored is left as it is until that version is back (older editors might drop what they can't show). **Restore** and **Retry** start a new session for the document; anything still typed in the old one is merged into it. Signing out removes the account's copies, cached bytes, and queued uploads; its confirmations (including signing this device out from Devices, and changing servers, which signs out every account) say when documents have edits that haven't been uploaded yet.
- **Chats** mention Files items in messages the same way: the composer and sent messages show them as cards beside attachments, **Add from Files** in its **+** menu adds them, as does typing `@` (matching items show in a list just above the message field), and sent links open the items. The Pulpo Agent menu (native on iOS) offers **Changes to Files** and, in a saved chat, **Files Access** (`ChatFilesAccessSheet`); a waiting Agent reply asks with **Deny**, **Allow for this chat**, and **Always allow reading Files**; **Ask before the agent looks through Files** is in Settings → Personalization → Agent. A reply that changed Files shows its changes with undo, redo, and suggestion review, including the conflict details when undo is refused. Tool activity names the `pulpo files` command the agent ran.
