1. Show Slide Trail setting is exposed but never reaches the trail renderer
Confidence: high static evidence; native visual confirmation outstanding. User value: an offered visual preference actually works.
Evidence:
- apps/keyboard-ios/App/PulpoKeyboardApp.swift:98 exposes Show Slide Trail, described as drawing a line behind the finger.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardCore/Shared/KeyboardSettings.swift:13 declares swipeTrail; :36 decodes it.
- A targeted rg for swipeTrail across App, Extension and PulpoKeyboardKit/Sources finds only those three references; no UI consumer.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/KeysView.swift:583-591 unconditionally starts/draws the trail when a glide begins; :455-457 adds subsequent path points. Its trail layer is added at :124.
Realistic trigger: keep Slide to Type on, turn Show Slide Trail off in Pulpo settings, return to the installed keyboard and swipe a word. Source predicts a visible trail still appears.
Expected: turning off the trail suppresses the line while glide entry, decoding and insertion continue normally.
Narrow fix direction: pass the already-loaded preference through KeyboardController to KeysView; gate only visual trail drawing/visibility, clear an active path if disabled. Avoid changing engine/glide semantics.
Proposed real-native check/control (after quiet END): use installed extension with settings access available; confirm settings load on return, then record the screen during matched swipes with trail OFF and ON. OFF must show no path; ON must show it. Assert the same word is inserted in both. Include one EN swipe, one ES swipe and one bilingual selection, plus tap typing control. Do not claim success from merely inspecting the stored setting or replaying the renderer with a Boolean.

2. Emoji insertion and deletion bypass Pulpo's Sound toggle
Confidence: high static bypass; audible behavior depends on iOS/system click settings and needs physical-device confirmation. User value: quiet typing remains quiet across emoji interactions.
Evidence:
- apps/keyboard-ios/App/PulpoKeyboardApp.swift:120 offers Sound for key clicks (conditional on system Keyboard Clicks).
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/KeyboardController.swift:622-624 gates ordinary key clicks on settings.sounds.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/EmojiPanelView.swift:291-295 calls UIDevice.current.playInputClick() unconditionally for grid insertion; :417-420 does likewise for initial/accessibility delete.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/EmojiSearchBarView.swift:139-142 unconditionally clicks for choosing a search result.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/PulpoKeyboardViewController.swift:7 opts into system input clicks unconditionally. Thus the keyboard-wide UIKit audio-feedback gate does not encode Pulpo's Sound setting either.
Realistic trigger: enable iOS Keyboard Clicks, disable Pulpo Sound, verify letter taps are silent, then insert an emoji from picker or search or tap picker delete. These paths still request system clicks.
Expected: Pulpo Sound off suppresses those clicks too; Sound on preserves system Keyboard Clicks behavior.
Narrow fix direction: route emoji/search input-click requests through the same preference-aware feedback owner as ordinary keys, or expose a shared sound gate refreshed with settings. Keep haptic preference and text actions independent. No change to learning/history storage needed.
Proposed real-native check/control: on a physical iPhone with silent mode off and fixed audible volume, system Keyboard Clicks ON, exercise ordinary letter, picker insertion, picker delete and search-result insertion in a native host, Sound OFF then ON. Use microphone/audio observation rather than screenshots alone. OFF should be silent for all; ON should produce their intended clicks. Repeat with system Keyboard Clicks OFF to ensure Pulpo never overrides the system setting; verify emoji/text edits still occur. EN/ES/bilingual setting should not affect this gate. No runtime claim is made here.

3. Emoji search can enter a disabled space-bar trackpad and drop its separator
Confidence: high static event-path evidence; native gesture confirmation outstanding. User value: multiword emoji searches remain editable without a misleading trackpad state.
Evidence:
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/KeyboardController.swift:1237 reports keysViewAllowsCursorMovement false while searching; :1179-1183 deliberately refuses host cursor movement in search.
- apps/keyboard-ios/PulpoKeyboardKit/Sources/KeyboardUI/KeysView.swift:413-416 nevertheless schedules enterCursorMode on a space hold; :461-464 also enters on a >30pt slide.
- :594-601 checks only tap mode, then dims all key labels and gives emphasis feedback; it never checks keysViewAllowsCursorMovement.
- :435-441 sets cursorMoved true before calling the delegate, even when the search controller discards movement. :524-528 then withholds space activation on lift because cursorMoved is true.
- KeyboardController.swift:802-807 would normally append the separator to the query. EmojiSearch.swift:17-30 permits exactly one trailing space after a nonempty query.
Realistic trigger: in emoji search type red (or cara), hold space >0.5s and drift >=9pt before lifting; alternatively slide >30pt to enter and move another >=9pt. Labels dim even though no search cursor exists, and the intended separator can be consumed, so the following word joins the previous one.
Expected: when cursor movement is unavailable, the space gesture should stay an ordinary space interaction, retain labels and append one separator on release. The host text/selection must remain untouched. Normal keyboard space trackpad continues working.
Narrow fix direction: gate cursor entry centrally in enterCursorMode on delegate permission (covers both hold and slide callers), preserving ordinary tap/release routing. Consider guarding cursor processing too if permission can change mid-contact; mode changes already cancel touches.
Proposed real-native check/control: in actual extension search enter red, perform a held space with 18pt drift, then type heart; inspect search field accessibilityValue for red heart and watch for absent label blanking. Repeat cara + held-space + feliz in Spanish and bilingual modes. A plain-space tap is positive input control; ordinary host-field space hold+drag must still move the host cursor, suppress the inserted space and restore labels on lift. Search host text/selection must stay unchanged until choosing an emoji. Add quick >30pt slide and stationary held-space cases; the latter should still append a separator. Native input is essential because direct delegate calls cannot establish this touch-mode bug.

Selection
These three are narrow visible mismatches grounded in offered behavior. No broader localization, text-size, one-handed or accessibility feature request is proposed from this sweep without clearer user-visible evidence. Findings 1 and 2 share a preference-integration theme but touch different visual/audio paths. Finding 3 is independent of engine accuracy and can be fixed within UI gesture routing.
