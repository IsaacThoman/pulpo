Independent pre-freeze R35 account lifecycle review
Review method: static source review only; no implementation changes or execution.
All source references below are relative to /tmp/pulpo-r35-account-lifecycle/apps/keyboard-ios.

Disposition
-----------
Do not freeze the current runner/evidence contract unchanged. Two definite runner gaps prevent its reports from proving the promised primitive counts and complete settlement. A pending-login refresh rule also needs an explicit interpretation before independent expectations are frozen. I found no unconditional stale-login or stale-refresh publication bug under serialized UI/runner execution in the clearly specified common schedules. This is not an execution pass, baseline comparison, or performance endorsement.

BLOCKING ISSUES

B1. HTTP primitive counts measure reservations, not HTTP issuance; unreserved requests escape the final unreleased-request check.
Evidence: AppTests/AccountLifecycleR35BenchmarkTests.swift:116-139 increments an HTTP counter only when awaitRequest removes an entry from AccountHTTPGate. AccountLifecycleR35Tests.swift:16-24 records actual issuance separately in enqueue/history. BenchmarkTests.swift:190-198 checks only driver.requests (already-reserved requests), not the gate's pending queue, and reports the reservation-derived counts as counts.
Consequence: an unexpected extra request, an automatically cancelled unreserved refresh sibling, or an unreserved logout can appear in httpIssued while being absent from counts and from Unreleased requests. A case can therefore have zero reported failures despite incomplete request accounting. Counts are not inferred from correctness, but they still are not the public protocol's counts of issued HTTP by method/path. The raw issuance strings make some discrepancies discoverable manually; they do not repair the reported counters or settlement check.
Required before freeze: count at the issuance seam, retain issued/reserved/released/cancelled disposition per request, and verify all issued requests are accounted for. Explicitly retain transport-cancelled work as such rather than silently clearing the pending queue. A fixture author should not have to know every request an implementation unexpectedly emits in order for those requests to be counted.

B2. Remote logout has no completion barrier, and teardown does not establish complete settlement.
Evidence: App/AppModel.swift:265-267 launches an untracked Task for logout. BenchmarkTests.swift:15,95-115 tracks login/refresh tasks only; waitTask checks that dictionary at 147-150, and reload/end-of-case settlement use that dictionary at 165-167,190-192. respond at 140-146 only delivers URLProtocol callbacks, as the protocol correctly warns; it does not await the logout Task. dispose at 42-47 cancels the network and waits at most 500 polling iterations for tracked work, then clears stores without retaining a teardown failure. Reports are captured before dispose (195-199).
Consequence: reserving/releasing a logout is not proof that the actual logout call has returned. The public operations cannot express a deterministic barrier for the claimed late-logout-versus-new-login completion test or establish that every task is settled before reload/end of case. Without an awaitRequest for logout, signOut(remote:true) followed by a signed-out checkpoint can pass before logout even issues; the only remote operation can be cancelled by disposal and omitted from the report. Work surviving the bounded disposal wait is not reported, and the next Driver resets a shared static gate.
Required before freeze: expose/track completion of remote sign-out work (an observational completion seam is sufficient), add a usable barrier or explicitly mark this proof unavailable, and retain failures if final drain/teardown does not settle. Preserve the case-local event history through settlement. These changes concern proof completeness; the candidate logout closure itself captures the old client and contains no account-clearing callback, so I did not find a source path by which its late completion clears a replacement.

B3. Clarify whether refreshes STARTED during a pending login remain disqualified after that login fails.
Evidence: AppModel.swift:192-196 advances accountGeneration at login authorization. refreshAccount at 234-240 captures that generation even when signInAttempt is nonnil. Eligibility checks signInAttempt == nil only at completion. An ordinary failed signIn clears signInAttempt in defer (207) without advancing accountGeneration. Successful login (227), explicit authority revocation (202), and sign-out (261) do advance it.
Source-derived schedule, not a disclosed fixture: establish account A; start login B and hold its login response; start refresh R against A and reserve its config/me requests; fail B with an ordinary error and wait for B; then complete R. With successful R responses it can save/publish A's updated user/capability. With successful config and me unauthorized it can clear A. This happens because the pending login has ended and R's captured generation is still current. Earlier refreshes started BEFORE B remain invalidated.
The public sentence, "A refresh launched while login is pending cannot publish or sign out that login", can be read as permanently excluding such refreshes, but can also mean protecting the pending/successful login only. Under the first reading the candidate violates the contract; under the second the observed behavior is permissible after failure. The succeeding sentence about successful login invalidating during-login refreshes does not settle the failed-login case. Do not decide this by observing later hidden expectations. State the allowed behavior for failure, transport task cancellation, and authority-only revocation now. If permanent disqualification is intended, capture eligibility at refresh start or otherwise preserve that disqualification. I classify this as a contract-freeze blocker, not an unconditional proven implementation failure.

NONBLOCKING FINDINGS / SCOPE LIMITS

N1. Keychain failure can destroy the previously stored account, outside the protocol's simulated failure coverage.
PulpoServices/SessionStore.swift:42-48 deletes the old item before attempting SecItemAdd. If add fails, AppModel.signIn throws session_storage (221-223), preserving the previous in-memory session/snapshot but losing its durable entry. refreshAccount similarly retains old memory after a failed save (248) even though the old durable entry may have been deleted. clear ignores delete status (SessionStore:51-52), so a failed deletion could leave credentials for reconstruction after sign-out. The protocol explicitly excludes simulated Keychain write failures; these are product correctness limitations rather than failures demonstrated within that declared runner scope. Atomic update/preservation and actionable deletion failure handling deserve follow-up.

N2. "Reload" proves same-process Keychain reconstruction, not independently durable snapshot persistence.
BenchmarkTests.swift:165-167 constructs another AppModel using the same UserDefaults object and URLSession. AppModel.init:65-70 loads Keychain and immediately republishes the snapshot before the check. Thus reload can repair an incorrect snapshot before inspecting it. KeyboardCore/Shared/AppGroup.swift:110-113 maps absent/corrupt snapshot data to signedOut, so signed-out checkpoints do not prove that an actual snapshot was written and decoded. Checking a decoded AccountSnapshot also would not detect an extra token key in the raw JSON. The actual candidate snapshot type and publisher contain no token, which supports that property by source inspection; the runner does not independently assert raw absence. Use a pre-reconstruction raw snapshot assertion if claiming durable snapshot or token-absence proof. No process restart, UserDefaults disk flush, crash consistency, or protected-data behavior is established here.

N3. Storage counters are event-seam counts, with narrower semantics than the public wording suggests.
AppModel.swift:221-224 and 248-249 emit "save" only after a successful save, so unsuccessful save invocations are omitted. "clear" is emitted after calling a void clear regardless of its OS result (269-270). "publish" is emitted after snapshot.save returns (279-280), not after independent persistence verification. Initial model construction and every reload also publish and increment the same counter (BenchmarkTests.swift:33-40; AppModel:70). Within successful Keychain operation assumptions these are useful call-site counts, but they are neither all attempted Keychain primitives nor physical disk-I/O counts. Document their exact units, including init/reload and exclusion of disposal, before comparing cost.

N4. Editable credentials can diverge from an in-flight submission; UI behavior is not covered by this runner.
SignInView.swift:14-32 leaves server/email/password editable while working; only submit is disabled (68). SignInAttempt.swift:8-12,70-74 resets challenge/error on edits without revoking the pending task. The task intentionally captures submitted values (26-27). A late success for those captured values still stores that account and calls onSuccess/dismiss even if fields have changed (38-40); an ordinary late error is shown without the credential-match guard used for two-factor errors (42-49). This agrees with the public model rule that login captures submitted inputs, so it is not a model-protocol blocker. The intended UX for edits during work should nevertheless be explicit in the separate native proof. Dismissal/Cancel/2FA Back do call revoke plus Task.cancel; I found those routes connected in the actual UI (SignInView:39,76-83; SignInAttempt:55-67).

N5. Task outcome vocabulary and operation-start barriers need accurate documentation.
The public protocol says waitTask records success/error/cancelled. The actual runner always records refresh as "finished" (BenchmarkTests.swift:108-115), because production refreshAccount consumes its errors. Login transport cancellation can be recorded as error:0:network rather than cancelled because PulpoClient.perform converts URLError cancellation into PulpoError.network (PulpoClient:119-126); cancellation is reported literally only when a CancellationError is thrown (BenchmarkTests:103-105). This is an observable API limitation, not evidence that cancelled tasks published. startLogin synchronously acquires authority before creating its task (92-100), matching SignInAttempt.submit. startRefresh has no corresponding entry/capture barrier: its model invocation happens inside the scheduled Task. Schedules requiring a refresh to have captured A before sign-out/new login should use the appropriate issued-request barrier, rather than assume that the JSON start step proves entry into refreshAccount. Likewise, respond alone is never a completion checkpoint.

N6. The executable runner does not enforce the complete public fixture schema.
BenchmarkTests.swift:180,185 accepts a missing/incorrect steps array as an empty schedule, with no mandatory checkpoint or task expectation. Missing IDs/purposes are defaulted in the report (195). Cross-case ID/host uniqueness and presence/types of every required expected field are not comprehensively validated. The final XCTest assertion counts failures but deliberately excludes unavailable operations (203-205); callers must not present that XCTest result alone as full protocol coverage. An independent schema seal may exist elsewhere, but was deliberately not inspected. Keep schema validity and availability as explicit independent prerequisites.

CANDIDATE / CALLER ALIGNMENT FOUND BY SOURCE REVIEW

- Actual UI submit calls beginSignIn synchronously before spawning the task, exactly as candidate startLogin does. Cancel and disappear synchronously revoke that specific UUID and cancel the owned task. Revoking an older UUID cannot revoke its replacement.
- signIn checks task cancellation and UUID authority before network, between config and login, and before persistence. Submission values are captured, ordinary network/decode/2FA failures do not directly clear the account, and a stale signIn defer cannot clear a newer UUID. There is no await between the last authority check and the save/memory/snapshot commit.
- refresh starts config and me concurrently, awaits config first, and commits their results together. Its checks use generation, latest refresh identity, pending-login state, instance/token, and cancellation. latestRefresh is not restored on failure/cancellation, preventing an older refresh from regaining authority. Login authorization/success and sign-out invalidate prior generations. Config-first error precedence agrees with the public warning.
- Explicit sign-out revokes login/refresh authority before synchronous local clear and snapshot publication. Remote logout captures the old bearer/client and performs no subsequent local clear.
- PulpoClient endpoint methods, request JSON fields, bearer construction, and decoder shapes match the listed valid protocol shapes. Nonempty two-factor code is included; empty/nil code is omitted. The actual snapshot struct has only signedIn/displayName/instanceHost/dictationAvailable.
- PulpoKeyboardApp.swift:14-17 starts refresh from scene activation; 207-208 and 374 present SignInView; 358 calls signOut with its production default remote:true. The runner intentionally defaults its explicit signOut operation to remote:false as documented. DictationService.swift:203-220 also has an unauthorized sign-out callback: its upload has cancellation/lifecycle guards, and account replacement/sign-out cancels active dictation in AppModel:225-226,264. Audio/upload schedules remain outside this runner.
