Baseline source review: `PreviewHost` lazily owns its document and weakly references its editor. `TextViewDocument` has an `unowned` host and dereferences it for every context read and mutation. `KeyboardController` weakly references its host but strongly owns its engine; the engine strongly owns its document. `PreviewInputView` strongly owns its controller. Coordinator removal invalidates and then releases the host/controller; direct host release bypasses invalidation. Invalidation alone clears the editor but cannot make a later unowned host dereference safe.

The three native `@MainActor` XCTest checks cover retained input/controller/engine/document across direct host release without invalidation; invalidation with a deliberately living host and selected editor; and a standalone actual document after input/controller/engine/host release. Weak probes assert deallocation before stale access. Only the invalidation check deliberately retains the old host. Direct-release fixtures retain the old editor so stale writes remain observable. Each check exercises working live editing, all four context/state properties after detachment, stale insert/delete operations, and replacement-editor text/selection isolation with continuing live replacement edits. Retained engines also receive insert/delete and controller reconciliation in the first two checks.

Objections and limits: retaining the old host would conceal the defect; changing `unowned` to a strong reference would prevent a crash but violate the deallocation assertions. Editor absence alone is insufficient, because these fixtures keep editors alive. The baseline is expected to trap on the first post-deallocation context read; a native crash is a red result, not a passing negative test. A candidate must support both absent-owner and invalidated-living-owner cases. No cursor-offset/Character math, R17 content, asynchronous scheduling, SwiftUI mount/dismantle behavior, or focus/window routing is claimed by these narrow document-lifetime checks. Controller/resource initialization may use the app's ordinary resource/settings services; no test injects a fake engine or document. Source inclusion is via the existing `AppTests` directory in `project.yml`; project generation/compilation remains for the parent runner.

Source rationale: `PreviewInputView.init` constructs a `UIInputView`, enables self sizing, changes the root view's background, and attaches the controller's root UIKit hierarchy. The input strongly owns the controller, which strongly owns the engine. Its height callback captures the input weakly; the controller's host, view delegates, bar update callback, notification callback, and emoji-resource task use weak references. Initialization calls `sync()`, which schedules a weak-self main-queue bar update, and starts the resource task. Thus the inner autorelease pool drains local autoreleases but does not run deferred UIKit/layout or main-queue work. A single deferred input-view retain would account for all three surviving probes. Deferred UIKit retention is a source-consistent hypothesis, **not a measured retaining-path diagnosis**; no memory graph or corrected native run was available in this round. A persistent ownership defect remains possible and must still fail the corrected check.

Correction: assert the host is nil immediately, then poll only the four weak probes while pumping the main run loop in 10 ms slices, each within an autorelease pool. Weak-probe evaluation also has its own pool so inspection does not carry autoreleased objects across slices. Stop as soon as all four are nil, or at a monotonic two-second deadline (checked between slices; individual UIKit callbacks can overrun a slice). Then execute the original four nil assertions and unchanged all-four-nil guard. A timeout is an assertion failure, never a skip or successful early return. No owner is invalidated, detached, manually torn down, or newly retained to force release. The document and old editor are explicitly kept alive together through every post-release read and mutation; all inert-state and old/replacement text/selection assertions remain unchanged. The document must still be an actual `TextViewDocument` obtained from the live engine, and the host must actually deallocate before deferred work is drained.

Objections and remaining validation: this relaxes the fixture's immediate consumer-release timing assumption, not its requirement that input/controller/engine/host are all deallocated before stale access. Main-run-loop draining can run unrelated app work; the fixture still installs no window, focus, coordinator, or editor input-view connection and claims no scheduling coverage. Two seconds is a bounded test allowance, not a production lifecycle guarantee or a measured UIKit release duration. If any probe survives, the standalone behavior remains untested and the test remains red; do not bypass the guard or increase retention to reach the assertions.
