Reviewed only the current `KeyboardEngine.swift` candidate diff and relevant engine/controller source, including the pre-freeze context-initialization fix and reuse of `.automaticSpace(respace: true)` for the newly added right gap. ## Assessment

The final pre-freeze addendum below supersedes the initial suitability assessment: an existing executable exact-output control conflicts with the new right-gap behavior. Under the frozen acceptance rule, the candidate must be rejected without tuning or expectation changes. The earlier source assessment is retained as review history.

The candidate is suitable for consideration as a deliberately narrow prose-insertion experiment, subject to unchanged frozen evaluation. It is not evidence of passing outcomes. It preserves the existing R5 left predicate, default/raw/emoji right-side behavior, single insertion primitive, and native privacy guards. It makes no dictionary/ranking/correction changes. I found no new host-prefix/suffix mutation or selection-order hazard in the diff.

Do not describe it as resolving external insertion generally: only explicit `spacing: true`, policy-allowed fields, visible contexts, letter/whitespace payloads, and English/Spanish letter suffixes qualify. Complete sentences, contractions, quotations/bracketed payloads, punctuation-only payloads, restricted fields, and several hidden-context situations intentionally remain misses. The original contract names some of these as targets; keep their failures and do not silently rewrite expectations.

## Findings and limitations

1. **Fresh-engine initialization concern resolved before freeze.** The initial inspected diff read `expectedAfterContext` before the first call to `prepareExpectedContext`, so a direct first insertion could miss an otherwise eligible right gap. The reviewed revision now calls `prepareExpectedContext()` immediately after reconciliation and before spacing decisions (`PulpoKeyboardKit/Sources/KeyboardCore/Input/KeyboardEngine.swift:464-465`). This initializes the logical prefix/suffix/selection when absent, does nothing when already initialized, and adds no document primitive (`:1217-1226`). Existing insertion preparation remains a harmless no-op (`:1154-1161`). No new API precondition to call `documentDidChange` is needed. Normal native controller initialization already does call it (`Sources/KeyboardUI/KeyboardController.swift:321,373`). Source reasoning supports the fix; no runtime pass is claimed here.

2. **The irreducible smart-API join ambiguity remains.** The letter/whitespace shape filter (`KeyboardEngine.swift:490-491,503-506`) admits ASCII identifiers and word fragments. At a visible start, `pre` before `fix`, or `foo` before `Bar`, gains a space under the candidate. A selected stem replaced before an existing `s` has the same ambiguity. These are independent source examples, not observed test cases. Because opt-in transcript/prose semantics are the stated narrow scope, this can be an explicit product tradeoff. It cannot be called safe technical recognition or universal preservation of intentional joins. Raw/literal callers are protected by the `spacing` gate; ambiguous `spacing: true` inputs are not distinguishable by the available evidence.

3. **Immediate punctuation now reuses established automatic-space semantics.** The candidate sets `.automaticSpace(respace: true)` only when it actually appends the new right gap; all other external insertion paths retain `.typed` (`KeyboardEngine.swift:494-499`). Existing literal punctuation handling then deletes that gap, inserts attaching punctuation, and inserts a gap afterward (`:301-304,319,325,328`). This supports an immediate comma/period followup while preserving the initial caret after the gap. It introduces three followup primitives whose exact queued ordering must be checked; it does not split the original selection replacement. Reviewing all `.automaticSpace` uses found no inherited correction/glide rejection, whole-edit delete, or host Undo behavior. Language-stack replacement intentionally preserves this spacing state (`:241-245`). Two limits remain: punctuation relocation requires `policy.smartSpacing`, which is false when smart punctuation is disabled (`Sources/KeyboardCore/Input/InputTraits.swift:71`); and the first followup sets `lastEdit = .typed`, so consecutive punctuation does not keep moving the gap. For example, a second `!` after a first `?` follows the restored gap. These are source-derived limitations, not test observations. Retain exact followup failures; do not claim general punctuation-run handling.

4. **The policy restriction is a new conservative right-side restriction, not a pre-existing explicit-spacing mandate.** Existing left spacing is gated by `spacing || phantomSpace`, while the new right spacing additionally requires `policy.autoSpaces` (`KeyboardEngine.swift:477,487`). Input policy disables `autoSpaces` for private/address/numeric fields (`Sources/KeyboardCore/Input/InputTraits.swift:62-72`). This narrows the new feature without altering their existing left semantics. Native transcript privacy remains independently enforced by destination guards. Report private/restricted engine behavior and native delivery availability separately.

5. **Visibility and queued delivery are handled conservatively but remain host-dependent.** Requiring both actual contexts nonnil (`KeyboardEngine.swift:488`) avoids deciding from a newly hidden edge. Using the reconciled expected suffix (`:489`) avoids simply trusting an old live snapshot during queued own edits. Original `before`, rather than the output after prepending a left separator, determines the left boundary (`:492-493`), so an ordinary midword prefix does not automatically become eligible. These are appropriate restrictions. They rely on existing reconciliation/own-history semantics; a source review cannot establish callback delivery ordering or rule out an unobservable external host edit. A queue fake can verify primitive ordering and selection replacement, not actual UIKit execution.

6. **One combined insertion preserves the narrow edit model.** The candidate only appends to the payload string and calls existing `insertDocumentText(output)` once (`KeyboardEngine.swift:494-498`). That helper clears the logical selection and advances the optimistic prefix while leaving the logical suffix unchanged (`:1154-1161`). No cursor movement, host suffix deletion/reinsertion, or added text-document primitive is introduced. Existing whitespace, suffix punctuation, raw insertions, and emoji insertions receive no new right gap because their guards fail. This supports the intended conservation argument at engine level; unchanged exact tests must still establish it.

## Disposition

Send to the parent as a scoped candidate with punctuation/technical ambiguity and conservative target misses disclosed. The initial first-call issue is resolved by the reviewed pre-freeze fix. Native host Undo remains unavailable: there is no Undo registration/grouping in this insertion path, and one primitive is not proof of a host Undo group. Native selected/private transcript delivery remains blocked by existing controller guards, regardless of what a direct engine invocation permits. Freeze exactly one final candidate and runner before heldout disclosure; evaluate unchanged expectations, retain failures/unavailability, and reject on any executable regression required by the frozen acceptance contract.

## Final pre-freeze addendum: existing exact-output regression

At the parent's explicit request, inspected the existing production test method `PulpoKeyboardKit/Tests/KeyboardCoreTests/AccuracyEditingTests.swift:22-27`. No development/heldout cases or results were read. The parent reported the production regression-gate failure; this addendum independently evaluates the source assertion rather than claiming an independently executed test run.

`pendingCursorMovePrecedesTranscriptCapitalization` initializes the document to `A note. please `, moves the cursor to offset zero without a callback, invokes `insertTranscript("Hello again")`, and asserts the exact complete document `Hello againA note. please `. The method's name emphasizes capitalization and pending-cursor reconciliation, but its executable assertion also requires no additional separator. That exact text is an existing engine API contract; its motivation does not permit weakening its assertion during this audit.

The candidate's new behavior deliberately changes that output: after reconciliation the left side is a known visible start, the suffix starts with `A`, and the inserted phrase contains only permitted letters/whitespace. The new branch therefore appends a right gap, yielding `Hello again A note. please `. This is not the irreducible `pre`/`fix` or code-identifier ambiguity discussed above. It is an ordinary prose-shaped insertion whose new intended behavior conflicts with a pre-existing exact-output control. The R20 natural-prose hypothesis and that control cannot both be satisfied for this observable insertion without changing the behavior contract or adding an unsupported exception.

Under the frozen acceptance rule that any executable-control regression rejects the candidate, this is a decisive compatibility regression even if the new spacing seems preferable for prose. Do not tune to this fixture, change its expected output, rename it into an unavailable case, or exempt it because native asynchronous transcript delivery has stricter destination guards. It remains an executable direct-engine control; native reachability is a separate claim. Preserve the single-candidate/runner freeze and one sealed evaluation as audit evidence if proceeding with the parent's stated plan, then restore production and retain the rejection. Any future decision to revise the public API's right-boundary semantics and migrate existing contracts belongs to a separately authorized change, outside this frozen experiment.
