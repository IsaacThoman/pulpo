CONTRACT CONTRADICTIONS / DECISIONS TO FREEZE
- The intended behavior is coherent, but is not the current implementation. AppModel.swift:179–208 publishes login/refresh results without an attempt, presentation, account generation, or cancellation check. MainActor isolation (project.yml:69) serializes synchronous writes but does not prevent interleaving across awaits.
- SignInView.swift:60–102 launches an unretained Task. Cancel only dismisses; neither sheet presenter revokes authority on interactive dismissal (PulpoKeyboardApp.swift:207–209,374). Supersession is not normally exposed by the disabled working button, but AppModel accepts concurrent calls and DEBUG login is another caller. UI working/error/challenge/dismissal must also be owned by an attempt; guarding only credential publication is insufficient.
- Two-factor is an inline extra field, not a separate navigation destination. There is no two-factor Back operation. No server challenge token exists: retry resubmits credentials plus code after another config fetch. Specify Back as clearing code/challenge/error and returning to credential entry, or declare it unavailable; do not claim current navigation implements it. Ordinary failure resets working and allows retry; a two-factor-required response sets needsCode, suppressing its message when code is empty.
- A submitted server is already captured by AppModel before its first await. The fields remain editable during work; later submissions use their current values. Define credential/server edits during a two-factor challenge: currently needsCode/code persist across those edits. A local challenge must not silently migrate to another server/credential identity.
- “Refresh before a new login” needs an explicit linearization point: submission authorization versus successful replacement. Recommend new submission invalidates prior refresh authority immediately; failure/cancel may retain the previously stored account, but cannot reauthorize an old refresh.
- SessionStore.save returns Bool, which AppModel ignores; clear ignores Keychain status. AccountSnapshot.save silently tolerates nil defaults. Thus durable consistency is not guaranteed on storage failure. Freeze whether persistence failure is in scope; an in-memory runner cannot establish actual Keychain/App Group durability.
- Dictation ownership is a substantive uncovered obligation, not satisfied by login/refresh guards. Define account owner as an app-private session generation plus instance/token identity, distinct from request UUID and text destination. Snapshot displayName/host are not unique account identifiers.

ACTUAL LIFECYCLE PATHS
- Initialization loads the default Keychain session, creates DictationService/observers, supplies a live sessionProvider, installs an unconditional dictation unauthorized -> signOut(remote:false) callback, and publishes AccountSnapshot (AppModel.swift:48–62). Instantiation therefore has real app/bridge side effects; it is not an isolated runner seam.
- Sign-in: normalize server -> config GET -> login POST with captured credentials/server -> Keychain save -> memory session -> token-free snapshot. No automatic remote logout for abandoned login exists. PulpoClient.swift:116–122 converts transport errors (including cancellation) to PulpoError.network; task cancellation is not preserved as CancellationError. URLSession cancellation alone cannot establish the required no-late-publication property.
- Refresh: scene activation launches a fresh unretained task each time (PulpoKeyboardApp.swift:14–17). It copies the current StoredSession, starts config and me concurrently, awaits config then user, then saves/publishes that copy. Observed unauthorized errors sign out whichever account is current; other errors preserve cache. No partial config/user publication occurs. A config failure can determine the catch before a concurrent me failure; do not invent a broader “any endpoint 401 wins” rule without deciding it.
- Sign-out: optional fire-and-forget logout captures the current server/token; local Keychain clear, memory nil, and signed-out snapshot happen synchronously. It does not revoke login/refresh work or cancel dictation.
- Snapshot (KeyboardCore/Shared/AppGroup.swift:94–120) contains only signedIn/name/host/dictationAvailable; load defaults to signedOut. Extension startDictation reloads it and checks Full Access, signed-in status, capability, and private-field restrictions (KeyboardController.swift:814–842).
- Dictation start checks only that some session exists. Permission/recording attempt guards use request UUID plus generation, but no account identity. stop reads sessionProvider again and creates the upload client then (DictationService.swift:85–107,189–220): recording begun under A can upload under B. Once issued, upload uses its captured account, but late success can still publish after account replacement; late 401 can sign B out. Existing lifecycle guards protect recorder attempts, not accounts. Bind owner at start and invalidate/cancel on account boundary; scope unauthorized callbacks to that owner. A metadata refresh for the same authorized session should not transfer ownership.
- Keyboard pending UUID, recorder attempt generation, delivered marker, and DictationInsertionGuard protect request/destination delivery independently (KeyboardController.swift:932–1040). Preserve those checks and private-field policy; account hardening must not reassign a pending request or put credentials into the extension snapshot/bridge.

MINIMAL CONTROLLED-SUSPENSION RUNNER SURFACE (RECOMMENDATION, NOT PRESENT)
- Use the actual production account/presentation coordinator with injected transport and isolated persistence/snapshot sinks. Public operations need to cover open presentation, edit input, submit/retry, cancel/dismiss, two-factor Back, cancel the submitted Swift task, explicit sign-out, refresh, and reconstruct from the same isolated store. Call the same authorization/publication logic as AppModel/SignInView; a runner-only model does not prove caller integration.
- Controlled transport must enumerate issued config/login/me/logout operations with stable operation IDs, captured server/token/body, and release success/error independently. Account refresh config/me form one refresh operation. Cancellation must be observable and a controlled continuation must still be releasable after cancellation to assess authority rather than transport cooperation. No real networking required.
- Observable state: presentation/attempt identity and activity, working/error/challenge/code state, account generation and refresh sequence, memory StoredSession, persisted StoredSession, decoded snapshot, publication/write events, pending operation/task completion, and refresh disposition (applied/stale/failed). Keep test credentials isolated; snapshot must remain token-free. A drain/acknowledgment barrier is needed for deterministic completion, not elapsed-time guesses.
- Dictation proof additionally needs the actual owner capture/invalidation/callback boundary without audio: request/attempt ID, captured owner, current stage, account-change notification, and controlled upload/unauthorized completion through production ownership checks. Existing public DictationRequestLifecycle alone cannot prove account ownership or upload wiring.

CONCURRENT REFRESH SEMANTICS RECOMMENDATION
- Freeze latest-started refresh wins within one account generation, using a refresh sequence separate from the session authorization generation. Both success and unauthorized side effects require matching captured generation, session identity, and latest refresh sequence. Starting another refresh does not itself replace credentials or reassign dictation ownership.
- A newer-started refresh makes older results stale even if the newer request later fails/cancels; no fallback authority for older responses. Current eligible success commits config+user together; current eligible unauthorized retains local sign-out behavior; other failures preserve cache. An unauthorized sign-out must also revoke pending sign-in authority per contract. Alternatively choose single-flight/coalescing, but disclose it as a different policy before sealing. Current implementation is completion-driven and has no such policy.

UNAVAILABILITY TO DECLARE
- As inspected, no public executable account lifecycle coordinator, presentation cancellation/Back API, refresh generation seam, injectable AppModel transport/storage, or audio-free dictation ownership seam exists. PulpoClient does publicly accept URLSession; SessionStore accepts a service namespace; AccountSnapshot accepts UserDefaults. Those component seams do not exercise the actual app callers together.
- No runner was authored or executed in this review. Persistence reconstruction, actual Swift task cancellation timing, SwiftUI dismissal/focus/navigation, endpoint behavior, keyboard typing/search regressions, real App Group/Keychain behavior, and native accessibility behavior remain unverified. Full audio, physical devices, and VoiceOver remain outside the contract proof. Declare unavailable operations separately from failed supported operations; do not count a domain-only simulation as native/caller coverage.
