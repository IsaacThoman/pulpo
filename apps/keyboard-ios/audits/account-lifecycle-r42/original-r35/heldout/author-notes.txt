heldout-01: Successful first login publishes a durable account with enabled capability
Expected effects: One authorized session is saved and published; reconstructed stores retain the exact fake identity, host, token and enabled capability. Snapshot excludes credentials and token under the runner contract.

heldout-02: Successful refresh changes name and capability while retaining session identity
Expected effects: Login and eligible refresh each publish their coherent state; refresh retains host/token and stores the new name and dictation value durably.

heldout-03: Malformed login config cannot create an account
Expected effects: The deliberately wrong JSON scalar type produces a decoder failure before authentication; memory and persistent stores remain signed out.

heldout-04: Ordinary replacement-login failure retains the previous account and capability
Expected effects: A different host config and ordinary login failure do not replace any field of the previous saved account or publish attempted capability.

heldout-05: Two-factor challenge preserves cache and an explicit coded retry can replace it
Expected effects: Challenge leaves prior durable account intact. The next login uses its own submitted credentials and explicit code, then publishes only its own user/config. UI challenge and Back controls are outside this runner.

heldout-06: An older login success released after a newer success cannot replace the winner
Expected effects: Only the newest login may publish. Released stale success is discarded or ignored, with no restoration and no abandoned-session logout.

heldout-07: An older two-factor failure released after a replacement succeeds cannot affect it
Expected effects: Late superseded challenge cannot alter the replacement account; error/focus UI is unavailable and is not assigned an expectation.

heldout-08: A failed newest login does not restore publication authority to an older login
Expected effects: Newest failure preserves the preexisting account. Older success remains permanently unauthorized after supersession, even though the superseding login failed.

heldout-09: Authority-only revocation preserves cache and allows retry despite a late success
Expected effects: Candidate revokes only the specified login authority without transport cancellation. Retry wins and late revoked success cannot write. Baseline revokeLogin is unavailable, never a passing operation; common operations remain separately reportable.

heldout-10: Cancelling an issued login keeps the previous account and permits a fresh retry
Expected effects: Cancelled Swift work cannot publish; its already-issued response is explicitly released and may be recorded as discarded by transport. Previous cache survives until successful retry.

heldout-11: Local sign-out fences a pending first-login success
Expected effects: Sign-out clears all state synchronously and permanently revokes prior login. Late success has no save/publication authority; no remote cleanup is requested.

heldout-12: Local sign-out clears a cached account despite a pending replacement failure
Expected effects: All cached fields clear synchronously. Late ordinary replacement failure cannot restore cached identity, capability or session.

heldout-13: Remote sign-out captures old session and its delayed logout cannot clear a new login

heldout-14: Refresh holds a completed me response until config permits atomic publication
Expected effects: Me completion alone leaves all cached fields unchanged. Config completion permits the eligible refresh to commit user and capability together with original host/token.

heldout-15: Latest-started refresh wins against an older late success
Expected effects: Only the later refresh may update the cached name/capability. An older success cannot roll back either field; each request is reserved by FIFO barriers before subsequent starts.

heldout-16: Failed newer refresh irrevocably fences an older unauthorized refresh
Expected effects: Ordinary failure of the newest refresh preserves cache and does not reauthorize older work. Stale observed unauthorized must not sign out.

heldout-17: Cancelled newer refresh does not reauthorize older successful work

heldout-19: Config failure takes precedence over already-returned unauthorized me
Expected effects: Me returns unauthorized while config remains pending. Because config is awaited first and fails ordinarily, the refresh preserves cache rather than promoting me unauthorized over that failure.

heldout-20: Starting a login fences an older refresh even when login later fails
Expected effects: Login start invalidates earlier refresh authority permanently. Ordinary login failure preserves old account; the invalidated refresh cannot sign it out afterward.
