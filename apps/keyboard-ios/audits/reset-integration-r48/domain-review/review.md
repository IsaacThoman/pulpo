## Required corrections before author

1. **Separate last-operation status from observation success.** v1 says no learning result/count/zero projection is available unless read status is ok. There is no separate read-status property: `persistenceResult` describes the last attempted operation (`TouchModel.swift:38,67–72,105–126,170–176`). Nil init reports ok; a nil reload returns false/ok without any I/O. A successful persistent reload can return false/ok when its projection is unchanged. Conversely, expected bad learn false/invalid leaves the settled local projection available for no-mutation comparisons. Requiring current status ok for that comparison would reject the very invalid controls the contract requires. V2 requires ok for constructor/fresh durable-read truth, preserves settled local projection checks after invalid, and distinguishes reload's changed Bool from its observation result.
2. **Narrow file immutability to the actual guarantee.** v1 blanket persistent rejection/no-files effect is false for general persistence failures. Source path: otherwise-valid first admission calls acquireSlot before global (`LearnedDataPersistence.swift:470–489`; acquireSlot264–274); it can create/lock writer.0, then global flock returns busy (`275–281`). False has taught nothing, but file inventory changed. Uncertain false can retain an ineligible durable reservation; save can commit earlier work, cleanup can follow committed reset. This is not a new product defect: it contradicts the overbroad draft requirement. V2 limits learned-file **content** invariance to intentional front-end invalid rejection after settled construction/preseed/earlier work and with no concurrent/background activity. It makes no general no-durable-effect promise for busy/io/uncertain/cleanup.
3. **Exact casing runtime, not intuitive contextual Unicode.** Source uses Swift String.lowercased, then Foundation compatibility decomposition, then Swift scalar-category filtering (`Lexicon.swift:391–418`). TypedWord performs that per original Character (`SpellCorrector.swift:27–37`), target normalization is whole-string (`TouchModel.swift:107–115`). The draft's operation ordering is right, but “contextual lowercasing can therefore matter” invites a false runtime-specific expectation or NSString substitution. V2 retains the separate operations without asserting an unproved contextual difference. Independent diagnostics actually distinguish Swift from NSString (below).
4. **Make admission/status relations executable.** V2 explicitly maps >40 actual persistent samples to false/invalid (not resource capacity), minimum2 to normalized **bytes**, samples to intended-byte centers, nonfinite validation only at contributing positions, extra/nil taps to ignored/absent points, and whole-call rejection before teaching. It specifies same **accepted** sequence/order for persistent-vs-local relations; a local >40-sample call deliberately cannot be blindly included in the persistent reference. Full26offset order, finite outputs, numeric tolerance and strict operation/ID/schema checks must be frozen. It distinguishes intentional false/invalid from an unexpected unavailable/error result so the integration contract's “error cannot pass” cannot make expected rejection cases unachievable.
5. **Preserve blindness as well as source blindness.** Public API availability is for the eventual runner, not permission for an author to query TextNormalizer or TouchModel to manufacture expected outputs before sealing. Independent literal Foundation checks/reference are permitted; product calls/results are not. V2 says so explicitly. No fresh cases were authored here.
