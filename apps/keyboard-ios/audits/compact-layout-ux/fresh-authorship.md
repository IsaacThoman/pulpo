# Independent fresh verification inputs

These twelve inputs were authored by a separate delegated agent before inspecting production keyboard implementation, development cases, baseline reports, candidate changes, or verification outcomes. This author did not run tests or use any simulator. The case selection comes from the requested user-visible risk areas and a deliberately varied combination of language, container bounds, docking, orientation, text sizing and bold text. Independence does not assert statistical randomness or prior knowledge of which cases fail.

The companion JSON is an input set, not an execution report. `width` and `height` describe the available host envelope in logical UIKit points, not a claim about a particular physical phone. The production root should lay itself out using its preferred intrinsic keyboard height; do not force it to stretch to the envelope height. Record both host and actual production-root bounds. Portrait and landscape bounds exercise constrained and generous arrangements. The container may include safe areas; the executing harness must record their actual insets rather than silently treating all coordinates as usable key area. A simulated width matrix cannot establish physical-device reachability or human comfort.

The executor should freeze the candidate before reading or executing these cases. It should instantiate the actual production controller, root, bar and key views and use real hit testing or production interactions. It must record the exact supported text category used for `accessibility`, the mechanism used to apply bold text, the starting language state, and any platform restriction on docking or presentation. Accessibility settings that cannot be applied are blocked coverage, not passes. An unavailable affordance must be reported with its actual prerequisite or platform limitation.

For every case, record actual bounds and control identities, attempted actions and resulting visible behavior, missed or redirected hit targets, clipping or overlap that loses an action or meaning, and unsupported steps. Intentional truncation can pass when the full meaning remains accessible and the action remains reachable. Letter keys have no universal 44-point gate: assess distinct reachable targets, correct input, and layout integrity. Sample every visible control at its center, four interior quadrants, and the perimeter just inside each of its four edges, explicitly including the lower portion and lower corners. Use the actually rendered visible bounds as the target, avoiding arbitrary blank background. Verify that each sample routes to the intended production action and produces its expected input, state change or presentation; merely finding some non-nil hit view is insufficient. Restore state between samples where an action changes layout. Record the sample strategy and any untested control or region.

For controls requiring state, create that state through production behavior before testing the control. In particular, an unavailable Undo after a plain insertion does not prove inaccessible Undo. Permission-dependent microphone behavior should be distinguished from an unreachable microphone control. Presentation checks concern opening, geometry, dismissal and restored keyboard interaction, without extending into app navigation or draft retention.

The input author owns only `fresh-cases.json` and this authorship note. No held-out outcomes, screenshots, corpora, build logs or result bundles belong in these files.
